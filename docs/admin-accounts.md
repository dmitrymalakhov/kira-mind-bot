# Аккаунты и боты в админке

Раздел «Аккаунты и боты» создаёт отдельные Киры на одном инстансе и подключает к каждой своего Telegram-бота. Мобильное приложение не требуется. Один аккаунт обслуживает одного бота; один человек может подтвердить несколько независимых аккаунтов.

## Подготовка сервера

Нужен работающий сервис `kira-accounts` с постоянным `KIRA_PLATFORM_MASTER_KEY`, PostgreSQL и Qdrant. Используйте [режим нескольких аккаунтов](multi-user-api.md#запуск). Для существующей личной установки сначала выполните описанный там перенос текущего аккаунта: он сохраняет память и настройки и останавливает прежний polling. Не запускайте standalone-процесс с тем же ботом одновременно.

Overlay `docker-compose.accounts.yml` связывает админку с менеджером через `KIRA_ACCOUNT_AUTH_URL=http://kira-accounts:3300` и передаёт обоим сервисам одинаковые `ADMIN_USERNAME`/`ADMIN_PASSWORD` из приватной Compose-конфигурации. При запуске без Compose задайте их обоим процессам явно. Публичный веб-кабинет и социальный вход для этого сценария необязательны. Если сервис аккаунтов не настроен, раздел показывает причину и не предлагает создавать аккаунты.

Лимит `KIRA_PLATFORM_MAX_ACCOUNTS` по умолчанию равен 10. Каждая готовая Кира запускается отдельным процессом со своей БД/ролью, пространством Qdrant, runtime-каталогом, настройками и памятью. Инфраструктура и ключи моделей общие. Личная Telegram-сессия и данные оператора новым аккаунтам не передаются.

## Создать Киру

1. Войдите в админку и откройте «Аккаунты и боты» → «Создать аккаунт».
2. Задайте уникальный логин из 3–40 латинских букв, цифр или `_` и пароль от 12 символов. Сохраните их для владельца: пароль повторно не показывается.
3. В открывшемся окне укажите токен отдельного бота из `@BotFather`. Если бот уже обслуживается другим приложением, остановите его и отключите прежний webhook.
4. Откройте выданную ссылку в Telegram будущего владельца и нажмите Start. Ссылка действует 15 минут и подтверждает личность владельца; передавайте её только ему.
5. Дождитесь статуса «Работает». Статус обновляется автоматически, а ссылку можно снова открыть через «Продолжить подключение» после обновления страницы. Когда срок истечёт, введите токен ещё раз для новой ссылки.
6. Откройте бота и выполните `/ai_consent`: прочитайте фактический список получателей данных и явно разрешите AI-обработку. Эту же команду можно использовать для отзыва согласия. Создание аккаунта и Start сами по себе согласия не выдают и самостоятельный AI-фон не включают. Если каталог получателей не настроен, сначала настройте его на сервере.

Токен BotFather подключает только бота: личные переписки владельца требуют отдельной собственной Telegram-сессии. Подтверждённого бота можно заменить через «Сменить бота», сохранив аккаунт. Аккаунты режима `api_only` отображаются в списке без кнопки подключения Telegram.

При ошибке соединения сначала обновите список. Повтор той же формы с неизменёнными полями использует прежний ключ операции: аккаунт не создаётся повторно, а действующая ссылка не меняется. Пароли, токены и ссылки не сохраняются в browser storage.

## Переключение аккаунтов

Выберите аккаунт в поле «Аккаунт» сверху или нажмите «Управлять» в его карточке. Модели, самостоятельность, голос, личность и внешность, MCP, память, чаты, задачи, дневник здоровья и расходы AI открываются для выбранной Киры. Перезапуск из сервисного меню затрагивает только её процесс. Параметры окружения применяются после этого перезапуска; настройки из БД и MCP сохраняют прежние сроки применения.

Текущий раздел сохраняется при переключении. Старые чтения отменяются, редакторы создаются заново, а несохранённые правки требуют подтверждения «Отбросить и переключить». Пока выполняется запись, переключатель недоступен. UUID выбора хранится в `sessionStorage` конкретной вкладки; разные вкладки могут управлять разными аккаунтами. Секреты там не сохраняются. Неудачное подключение или удаление выбранного аккаунта показывает ошибку без перехода к данным другой Киры.

Пункт «Инстанс · общие подключения» открывает ключи провайдеров, адреса API и инфраструктуру. Идентификаторы владельца, Telegram credentials и привязки хранилищ аккаунта не редактируются как обычные параметры окружения. Личные данные доступны после выбора конкретного аккаунта. Неподтверждённый Telegram-аккаунт сначала нужно подключить через Start и дождаться подготовки хранилища.

В accounts-режиме каждый запрос данных требует выбранный UUID. Сервер получает канонические DB/роль, owner principal, memory namespace и botId от менеджера; импортированная Кира сохраняет исходные пространства памяти и БД. Контекст запроса хранится в `AsyncLocalStorage`, без переключения `process.env`. Runtime-файлы привязываются к каталогу UUID с проверкой символических ссылок. Настройки окружения аккаунта хранятся зашифрованно с allowlist и проверкой ревизии. Изображения и экспорт используют `/api/account-scopes/{uuid}/…`; внутренние auth/accounts endpoints вложить туда нельзя. В standalone-режиме прежние пути продолжают работать.

Админка проверяет наличие `bot_settings` без `CREATE TABLE` от имени аккаунта. Подготовка схемы остаётся задачей менеджера/миграции: импортированной роли достаточно доступа к существующим таблицам, права создавать таблицы ей не требуются.

Добавление и изменение памяти проходят через parent policy выбранного аккаунта: операторский вход не заменяет согласие владельца на AI и не обходит квоты.

## Переименование и замена бота

«Переименовать» меняет название аккаунта в карточке и переключателе. Допускается до 80 символов, в том числе кириллица. Логин для входа, пароль, UUID и данные сохраняются. Название самой личности Киры по-прежнему задаётся в разделе «Личность».

«Сменить бота» доступно для подтверждённого активного Telegram-аккаунта. Укажите новый токен BotFather и введите логин этого аккаунта для подтверждения. До проверки токена и сохранения новой привязки прежний бот продолжает работать. При конфликте с другим аккаунтом, недействительном токене или webhook замена отклоняется. После сохранения перезапускается только выбранный worker. Можно также обновить токен того же бота после перевыпуска в BotFather.

UUID, владелец, база и роль, пространства памяти, настройки, личная Telegram-сессия, API-токен, чаты и расписания задач сохраняются. Владелец должен нажать Start у нового бота; в прежние группы нужно добавить нового бота и выдать ему права. Telegram-сообщения прежнего бота остаются в его чате. Текст истории аккаунта сохраняется; старые ID сообщений и незавершённые кнопочные формы не используются для управления сообщениями нового бота. При смене бота его update offset начинается заново; при обновлении токена того же бота offset сохраняется.

Открытая форма содержит ревизию аккаунта. Параллельная смена бота, владельца, названия или credentials требует закрыть форму, обновить список и подтвердить действие заново. Повтор после потери ответа с тем же ключом не выполняет замену второй раз; токен удаляется из формы после успеха и не сохраняется в browser storage.

## Безвозвратное удаление

«Удалить аккаунт» → введите его **логин** → «Удалить навсегда». Это удаление всех данных аккаунта, без архива и восстановления через интерфейс. Сервер сразу блокирует доступ, фоновые AI-операции и сессии и создаёт долговечную задачу. Worker удаления останавливает процесс, отзывает связанные provider credentials и очищает принадлежащие аккаунту БД/роль, Qdrant, runtime-файлы и записи реестра. Соседние аккаунты и общая инфраструктура не удаляются. При ошибке очистка продолжится после повторного запуска; сообщение «Удаление начато» означает принятую задачу, а не мгновенное завершение всех шагов.

Нужен настроенный `KIRA_PUBLIC_DELETION_LEDGER_DIR`. Для импортированного аккаунта дополнительно требуется доверенный локальный `KIRA_PUBLIC_DELETION_MANIFEST_FILE` с подтверждением исключительного владения его базой, memory namespace и runtime-каталогом. HTTP не принимает пути и привязки хранения. При отсутствии подтверждения операторское удаление отказывается **до блокировки** аккаунта. Реестр tombstone применяется перед обслуживанием восстановленной резервной копии; правила и пределы хранения копий описаны в [контракте удаления](public-accounts-v1.md#durable-inbox-apns-and-deletion).

## Граница доступа

`GET/POST /api/accounts`, `PUT /api/accounts/{uuid}/bot`, `GET /api/accounts/{uuid}/pairing`, `PATCH/DELETE /api/accounts/{uuid}` и `POST /api/accounts/{uuid}/bot/replacement` требуют действующей операторской сессии; изменения дополнительно требуют same-origin, CSRF и ключ операции. Внешний операторский proxy пропускает только эти точные методы/пути. Публичная регистрация через `/api/v1/accounts/register` остаётся закрытой.

Админка обращается к фиксированному `/internal/operator/accounts`. Менеджер самостоятельно проверяет операторский пароль либо канонические browser/session/identity/account/grant социального оператора на каждом запросе. Одного bridge-secret, обычного Bearer пользователя или выбранного UUID для доступа недостаточно. Внутренний путь не включён в публичные proxy/gateway-инвентари. Пароль оператора передаётся только сервером админки на доверенный внутренний адрес; тела запросов и credentials не логируются.

Новые password-аккаунты создаются доверенным оператором сразу в режиме `telegram`; пароль хранится как scrypt hash, password identity и квитанция создания сохраняются одной транзакцией. Это не открывает публичную регистрацию. Токен и восстанавливаемый код Start зашифрованы account-bound ключом; списки и квитанции не содержат их. Удаление аккаунта стирает credential fingerprint и оставляет только служебную привязку ключа повтора к удалённому UUID, чтобы старый запрос не создал замену.

Проверки: `npm run test:admin-accounts-ui`, `npm run test:admin-account-switching-ui`, `npm run test:admin-account-management-ui`, `npm run test:unit` и PostgreSQL-регрессии `tests/admin-account-switching.test.ts`, `tests/platform-operator-accounts.test.ts`/`tests/platform-public-deletion.test.ts` с явным `KIRA_PLATFORM_TEST_PG_PORT` отдельной тестовой БД. Браузерные тесты используют синтетические API; они не проверяют реальный BotFather/Telegram или опубликованный сервер. Реальные пользовательские аккаунты в проверках не переименовываются, не переключаются на другого бота и не удаляются.
