# Повторный аудит архитектуры — 2026-10-26

Проверялся переход от маршрута по единственному intent к ядру с инструментами, скиллами и специализированными агентами. Проверка включала код входных обработчиков, исполнение зависимостей, write-ahead, подтверждения, продолжения, транспорт файлов и регулярные задачи. Производственные данные и реальные отправки для регрессий не использовались.

## Архитектурный вывод

Разделение ответственности соответствует проекту:

| Слой | Ответственность |
| --- | --- |
| Intake и классификация | Новая реплика отдельно от reply/forward, источник знаний, intent, память и сложность. Категориальный Decisions остаётся опциональной заменой этого этапа. |
| Ведущее ядро | Декомпозиция всего запроса, выбор следующего действия по результатам, зависимости, бюджеты и итог. Составной запрос не сводится к одному доменному агенту. |
| Скиллы | Доверенные процедурные инструкции, загружаемые по необходимости. Прав на выполнение они не выдают. |
| Инструменты | Схемы аргументов, серверный scope, эффекты и типизированные исходы. Параметры инструмента самостоятельны относительно основного intent. |
| Прикладные сервисы | Каноническая логика личности, evidence, хранилищ, отправки, подтверждений и расписаний. Её сохранение предотвращает появление второго источника правды. |
| Специализированные агенты | Собственные ограниченные циклы исследования, браузера, переговоров и изучения переписки. Родитель получает результат и состояние. |
| Планировщик | Запуск сохранённого запроса, изолированный журнал, учёт результата и пауза при неопределённости. |

Короткий путь обычного разговора, команды и готовые меню сохраняются. Общий адаптивный цикл нужен для составных действий и выбора инструментов, а дополнительная модель планирования на приветствии ничего не даёт. `legacy` оставлен для сравнения и отката; его наличие не означает, что обычный ход по умолчанию исполняется прежним executor.

## Обнаруженные и исправленные ошибки

1. **Вторая задача терялась в итоговом ответе.** Поиск при основном intent «напоминание» выполнялся, но итог мог содержать только reminder. Синтез теперь зависит от составной цели, а не только от основного intent.
2. **Составная фраза обходила ядро.** Старый memory handler перехватывал «забудь … и напомни …». Такие реплики передаются оркестратору через настоящий стек обработчиков. Детектор составных действий дополнен управлением задачами, файлами и другими существующими действиями.
3. **Подтверждение могло продолжить чужой запрос.** Выбор ожидающей операции только по имени `memory.forget` был недостаточен. Теперь используется серверный ключ конкретной записи; подтверждение и отмена не затрагивают соседние ожидающие запросы. При возобновлении архивной цели текущая ожидающая цель сохраняется.
4. **Параметр инструмента терялся между ходами.** Сохраняются сам вызов и его зависимости. После ответа повторяется только безопасно остановленный до выполнения шаг с новыми эффективными параметрами; уже выполненные мутации не воспроизводятся. Статусы зависимостей хранятся отдельно от сокращаемых свидетельств для модели. Отдельная новая команда не считается ответом на старое уточнение.
5. **Workflow чтения зависел от чужой классификации.** В составном запросе Telegram мог получить детали reminder и прочитать другой источник. Режим чтения, контакт/чаты и сохранение фактов теперь задаются аргументами инструмента. Уточнение контакта использует каноническую проверку личности.
6. **Доменные ошибки считались успехом.** Добавлены явные статусы для карт, ошибок изучения переписки и частично сохранённого batch напоминаний. Неоднозначное удаление использует общий identity guard; недоступная память не подтверждает удаление. Сохранение после выбора личности сообщает родителю о подтверждённом результате.
7. **Большой список терял ID.** Вместо отбрасывания целой выдачи при превышении контекстного лимита ресурсы выдаются страницами с `query`, `offset`, `limit`, `total` и `nextOffset`.
8. **Фон мог перезаписать живой журнал.** Регулярная задача имеет стабильный отдельный ключ хранения и идентификатор конкретного scheduled run. Доменный flush использует тот же ключ и отдельный snapshot: запись журнала не подавляет последующий flush изменений интерактивной сессии. Ожидающая задача переносится в интерактивную сессию контролируемым merge, сохраняя текущую цель.
9. **Планировщик игнорировал исход нового ядра.** `failed` больше не записывается как completed; `unknown/needs_input` сразу приостанавливают регулярную задачу. Результат неопределённой мутации не воспроизводится при повторной доставке того же запуска. Все артефакты, включая частично успешный результат, доставляются.
10. **Выбор периода не завершал шаг анализа чатов.** Callback группового анализа теперь сообщает подтверждённый результат ядру по request ID; ошибка не запускает зависимые изменения. Для перехода «изучение переписки → выбор личности» заменяется ключ подтверждения того же шага. Это работает и для `telegram.readMessages`, и для делегированного `study-chat`; после сохранения завершается также метадата дочернего агента.
11. **Старые строки ошибок и чужие pending-поля искажали статус.** У Telegram-сводок и анализа переписки появились типизированные внутренние результаты; прежние строковые адаптеры сохранены для старого UI. Успешное независимое чтение больше не ожидает чужой браузерный или медицинский сценарий.
12. **Повторная загрузка скилла вытесняла сохранённую очередь.** Продолжение восстанавливает инструкции ранее загруженных скиллов и следующих шагов до входа в цикл. Уже подтверждённый следующий шаг не зависит от того, повторит ли модель его после lazy loading.
13. **Контактные кнопки и фоновое уточнение теряли связь с фактом.** Кнопки получили стабильный ID уточнения, сохраняющийся при частичном сохранении. Старый выбор или отмена не затрагивают новый факт. Фоновое уточнение контактной памяти переносится вместе с журналом; конфликт с уже ожидающим уточнением явно приостанавливает задачу, не заменяя вопрос владельца и сохраняя частичные артефакты.
14. **Браузерный pending перехватывал новые задачи.** Реальные text/API handlers и intent override теперь различают самостоятельную новую команду и ответ на ожидающий вопрос. Незавершённая страница сохраняется; другая браузерная задача получает понятный отказ вместо молчаливой замены.
15. **Общее имя агента смешивало браузерные продолжения.** Подтверждения, отмены и IDs дочернего браузера связаны с конкретной session ID. Новая успешная браузерная задача не завершает чужое изучение переписки или переговоры; старые кнопки не отменяют новый сценарий. Возобновляется совпавшая архивная цель; отмена, ошибка и `unknown` снимают её очередь, не выдавая успех зависимым изменениям.
16. **Изоляция журнала не распространялась на живой браузер.** Lookup и cancellation проверяют канал или ledger фоновой задачи; ручной ответ фоновому браузеру сохраняет его scope и recurring-ограничения. Owner-lane по-прежнему сериализует работу с личным профилем. Если ожидающий workflow находится в другом канале, возвращается явный отказ, а не доступ к его странице.

## Проверяемые границы

- Реальный вход `processMessage` и реальный API-стек обработчиков, включая переход из старого memory handler.
- Параллельные чтения, последовательные изменения, неверные зависимости и ограничения цикла.
- Вопрос инструмента, повторное выполнение уточняемого шага, два ожидающих подтверждения и адресная отмена.
- Память, private/owner scope, отсутствие повторного retrieval при подготовленном пустом контексте.
- Фактическое сохранение reminder, частичная ошибка, отсутствие повторного сохранения транспортом.
- Параметры Telegram вне основного intent, ошибки карт и изучения чата.
- Отдельное хранение фонового журнала, восстановление scheduled request key, пауза планировщика и доставка нескольких файлов.
- Сборка с 14 `SKILL.md`, общие regression-наборы и режим `legacy`.
- Реальные callback-обработчики группового анализа и выбора периода, передача подтверждения личности, типизированные Telegram-ошибки, старые контактные кнопки и конфликт фонового уточнения.
- Реальные входы браузера: новая команда при pending, продолжение архивной фоновой цели, старая кнопка отмены, несовпадающий ID дочернего агента и отказ продолжать зависимые изменения после отмены, ошибки или неопределённости.

Итоговая проверка: полный `npm test` прошёл; после последних правок отдельно повторены сборка сервера, проверка скомпилированной поставки и весь unit-набор в основном режиме и `legacy`. В каждом режиме — 541 тест: 540 успешно, один пропущен, ошибок нет. Набор `agent-runtime*.test.ts` содержит 84 проверки, включая регрессии callback-ов, фоновых конфликтов и браузерных входов. Группа `test:ts:interaction` также прошла.

## Практические ограничения

Это прикладное ядро с четырьмя известными ролями агентов. Динамический запуск произвольного кода или неограниченная рекурсия агентов проекту сейчас не нужны. Отдельные доменные workflows сохраняют свои модели и специализированные циклы; скиллы не заменяют их исполняемую бизнес-логику.

Персистентный журнал не восстанавливает живой объект браузера или переговоров после потери процесса. Для многодневного универсального workflow engine потребовалась бы отдельная модель durable jobs и миграция этих сервисов. В текущей реализации неопределённые эффекты не воспроизводятся автоматически.

Одновременно исполнять несколько уточнений личности в одном legacy contact-memory UI нельзя: конфликтующий фоновый запуск ставится на паузу с объяснением и требует нового ручного запуска после завершения текущего уточнения. Самостоятельно объединять факты разных задач в одно подтверждение недопустимо.

Автотесты используют синтетические данные и подменяют внешние API. Перед включением на рабочем инстансе остаются ручные проверки выбранных моделей, задержек, реального Telegram и конкретных сайтов по [сценариям руководства](agent-runtime.md#проверка-ветки). Доступность Decisions на конкретном gateway отдельно не подтверждалась платным вызовом.
