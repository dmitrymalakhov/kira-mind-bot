# Отдельная Кира для каждого аккаунта

Сервис аккаунтов позволяет зарегистрироваться через API, передать токен своего Telegram-бота и получить собственную Киру. У аккаунтов отдельные базы PostgreSQL с отдельными DB-ролями, коллекции Qdrant, диалоги, настройки, память Киры, напоминания, регулярные задачи, файлы, браузерные профили и cookies. Telegram и API одного аккаунта используют общие знания; история диалогов разделена по каналам, как в личном API.

Один аккаунт подключает одного бота. Один бот принадлежит одному аккаунту. Вход выполняется по логину и паролю; токен BotFather служит только для подключения бота и не является паролем аккаунта. Прежний владелец может перейти в обычный аккаунт с сохранением своей памяти, настроек, переписок и доступа через API.

По умолчанию у новой Киры **нет доступа к личному Telegram и перепискам владельца**. Токен BotFather даёт только работу самого бота: сообщения, отправленные ему напрямую, и чаты, в которые его добавили. Для личных переписок нужна отдельно подключённая собственная Telegram-сессия. Фоновое чтение у новых аккаунтов по умолчанию выключено и включается явно через пользовательские настройки.

## Запуск

Нужны PostgreSQL с правами оператора создавать базы и роли, Qdrant и настроенные ключи моделей. Сначала собери сервер: `npm run build:server`. Сервис запускается командой `npm run start:accounts`; он не требует токена личного бота. Для Docker используй дополнительный файл:

```bash
docker compose -f docker-compose.server.yml -f docker-compose.accounts.yml up -d --build kira-accounts
```

При локальном Docker-запуске добавь используемый `docker-compose.local.yml` перед overlay аккаунтов. Соблюдай обычную идентификацию Compose project и существующие настройки storage из [локального запуска](local-run.md). Личный bot/admin контейнер перезапускать не требуется.

В `.env.production` задай **постоянный** `KIRA_PLATFORM_MASTER_KEY`: 32 случайных байта в hex. Сгенерировать его можно через `openssl rand -hex 32`; сохрани результат приватно, без Git. Этот ключ шифрует токены ботов и личные Telegram-сессии и выводит внутренние credentials. Резервируй его отдельно от PostgreSQL; изменение ключа требует миграции credentials. При несовпадении ключа сервис откажется запускаться.

Настройки:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `KIRA_PLATFORM_DB_NAME` | `KiraPlatform` | Отдельная служебная база аккаунтов |
| `KIRA_PLATFORM_HOST` | `127.0.0.1` | Адрес прослушивания вне Docker |
| `KIRA_PLATFORM_PORT` | `3300` | Внутренний API-порт |
| `KIRA_PLATFORM_DATA_DIR` | `runtime-data/accounts` | Приватные файлы всех аккаунтов |
| `KIRA_PLATFORM_MAX_ACCOUNTS` | `10` | Лимит регистрации по ресурсам сервера |
| `KIRA_PLATFORM_RESERVED_BOT_IDS` | пусто | Дополнительные боты оператора, недоступные для регистрации |
| `ACCOUNTS_PORT` в Compose `.env` | `8330` | Порт аккаунтов на loopback хоста |

Каждый подключённый аккаунт запускает полный отдельный процесс бота с собственными планировщиками. Выбирай лимит аккаунтов с учётом RAM и общего бюджета моделей. Ключи AI и адреса инфраструктуры общие; данные владельца, personality, browser credentials и Telegram-сессия оператора не наследуются. Операторская админка управляет прежним личным инстансом; панели управления аккаунтами в ней пока нет.

Запускай один сервис аккаунтов на служебную базу: PostgreSQL-блокировка не допускает второго управляющего процесса. После перезапуска пользователи и привязки восстанавливаются из БД, процессы запускаются заново, файлы сохраняются. При потере соединения блокировки процессы останавливаются, а менеджер перезапускается через Docker. Потеря HTTP-ответа не означает, что действие не выполнилось: сохраняй `Idempotency-Key` при повторе.

## Регистрация и вход

### Перенос текущего инстанса

Для уже работающей установки используй `python3 scripts/migrateCurrentAccount.py` для проверки, затем тот же вызов с `--apply` для переноса. Docker CLI должен быть доступен в PATH; при необходимости укажи `--docker /path/to/docker`. Скрипт использует общий preflight проекта и сравнивает приватную конфигурацию с работающим контейнером. Во время сборки прежний бот продолжает работать; на само переключение polling приостанавливается. Если новый runtime не проходит проверку, старый контейнер запускается обратно.

Перенос создаёт обычный аккаунт `current_user` с отдельной ограниченной PostgreSQL-ролью. Его база, таблицы, Qdrant-коллекции, память, IDs и напоминания остаются на месте; schema sync от имени новой роли выключен. Личность, self-memory, изображения, cookies и браузерные профили копируются в приватный каталог аккаунта. Ключи инфраструктуры, SSH-туннеля и клиентского CA туда не переносятся. Уже выбранные фоновые настройки и собственная Telegram-сессия сохраняются. Следующие изменения схемы импортированной базы выполняет оператор установки.

Прежний API-порт и его ключ продолжают работать через обычную аутентификацию аккаунтов. Старый долгоживущий ключ остаётся действующим до явного `/accounts/logout`; новые токены входа выдаются на 30 дней. Приватные логин, пароль и ключ сохранены в `runtime-data/accounts/import/current-account.json` с правами `600`. Этот файл не входит в Git и не должен публиковаться.

Скрипт включает `KIRA_ACCOUNTS_MODE=true` в Compose `.env`, после чего `scripts/ops/local.sh` использует менеджер аккаунтов. Прежний standalone bot остаётся остановленным в профиле `legacy`; не запускай его параллельно с аккаунтом, поскольку Telegram допускает только один polling-процесс этого бота. Операторская админка продолжает читать ту же базу и получает health/restart текущего сервиса аккаунтов.

### Создание нового аккаунта

Базовый адрес нового сервиса, например `https://accounts.example.com/api/v1`. Для новой установки он использует отдельный upstream; при переносе существующей установки сохраняется её прежний порт. Для внешних клиентов установи HTTPS reverse proxy перед портом аккаунтов. Ограничь JSON body 64 KiB, сохрани `Authorization` и `Idempotency-Key`, разреши ожидание AI до 600 секунд, отключи автоматическое повторение POST и логирование заголовков/тел. Не публикуй динамические worker-порты: они слушают только `127.0.0.1` внутри сервиса. Старый [личный mTLS gateway](public-api-gateway.md) допускает runtime-маршруты; для новых маршрутов регистрации и управления аккаунтом его allowlist расширяется отдельно.

Машиночитаемый контракт: [accounts.openapi.json](../api/accounts.openapi.json). Общие маршруты ссылаются на существующий контракт runtime, чтобы не дублировать его.

`POST /accounts/register` принимает:

```json
{"username":"example_user","password":"<личный пароль длиной от 12 символов>"}
```

Логин: 3–40 латинских букв, цифр или `_`, регистр не учитывается. Пароль: 12–256 символов. Ответ `201`:

```json
{
  "account":{"id":"<uuid>","username":"example_user","bot":null},
  "accessToken":"<персональный токен>",
  "tokenType":"Bearer",
  "expiresIn":2592000
}
```

`POST /accounts/login` принимает такие же поля и возвращает новый токен на 30 дней. Храни его в защищённом хранилище приложения. Пароль хранится как salted scrypt hash, access token — как SHA-256 hash. Неверный логин/пароль дают одинаковую ошибку. До 20 попыток регистрации/входа в минуту на прямой IP; до 120 обычных запросов на аккаунт. Если reverse proxy скрывает IP, настрой дополнительный внешний rate limit; недоверенные `X-Forwarded-For` не используются.

Все следующие запросы требуют `Authorization: Bearer <accessToken>`:

| Метод и путь | Результат |
| --- | --- |
| `GET /account` | Свой аккаунт и статус своей Киры |
| `GET /settings` | Режим работы, фоновые функции и причины их приостановки |
| `PATCH /settings` | Изменить режим и выбранные фоновые функции |
| `POST /accounts/logout` | Отозвать текущий access token |
| `PUT /account/bot` | Подключить своего Telegram-бота |
| `PUT /account/telegram` | Необязательно подключить личный Telegram для работы с переписками |
| `GET /account/telegram` | Проверить наличие личной Telegram-сессии без выдачи credentials |
| `DELETE /account/telegram` | Удалить личную сессию из аккаунта и остановить доступ к перепискам |

Аккаунт выбирается сервером по access token. Передавать `accountId`, `userId` или `chatId` для выбора чужой области нельзя. Восстановление забытого пароля и удаление аккаунта отдельными API-методами пока не реализованы.

## Подключение Telegram-бота

1. Создай отдельного бота в BotFather. Останови прежний polling/webhook для этого бота, если он был запущен. Сервис проверяет `getMe` и отказывается перехватывать работающий webhook.
2. Выполни `PUT /account/bot` с телом `{"botToken":"<приватный токен BotFather>"}`.
3. Ответ `202` содержит `pairingUrl` и `expiresIn: 900`. Открой эту ссылку в своём Telegram и нажми Start. Ссылку никому не пересылай: она подтверждает владельца.
4. Проверяй `GET /account`. Сначала статус `awaiting_telegram`, затем `starting`, затем `ready`. Если срок ссылки истёк, повтори подключение до завершения привязки.
5. Пиши в своего бота или отправляй сообщения через API с тем же токеном аккаунта.

Владелец определяется по реальному отправителю приватного `/start <одноразовый код>`, а не по ID из HTTP-запроса. Код истекает через 15 минут и не используется повторно. В одной транзакции привязка становится постоянной; случайное повторение запроса после подтверждения возвращает `409 bot_already_connected`, данные не сбрасываются. Замену подтверждённого бота через API эта версия не выполняет.

Механизм ссылки соответствует [deep linking Telegram](https://core.telegram.org/bots/features#deep-linking); получение updates и проверка webhook описаны в [Bot API](https://core.telegram.org/bots/api#getupdates).

## Работа со своей Кирой

После статуса `ready` доступны прежние маршруты [личного API](external-api.md#контракт): `GET /status`, `/capabilities`, `/history`, `/reminders`, `/tasks`, `/files/{id}`, `POST /messages` и `/actions`. Используй **токен аккаунта**. Внутренний токен процесса клиенту не выдаётся. На каждый POST сообщения или действия передавай `Idempotency-Key`.

Например, `POST /messages` с `{"text":"Привет, Кира"}` возвращает обычный массив `messages`. Поддерживаются общие команды, память, напоминания, регулярные задачи, изображения и браузерные задачи. Плановые уведомления приходят в Telegram этого аккаунта. Браузер направляет весь HTTP/HTTPS-трафик через прокси публичных адресов: локальные сети, Qdrant, PostgreSQL, metadata endpoints и внутренние API недоступны, включая DNS rebinding. Непубличные сайты пользователя в этом режиме недоступны.

## Режим работы и фоновые функции

После готовности Киры `GET /settings` возвращает `budgetMode`, каталог `budgetModes`, `telegram.personalSessionConfigured` и массив `features`. У каждой функции есть `key`, название, описание, группа, сохранённый флаг `enabled`, фактическое состояние `effective` и `blockedBy`. Причина `telegram` означает отсутствие личной сессии, `budget` — максимальную экономию, ключ другой функции — зависимость от её переключателя. Выключенная функция имеет `blockedBy`, равный своему ключу. Токены и содержимое сессий в ответ не попадают.

Для изменения используй `PATCH /settings`, например:

```json
{
  "budgetMode": "normal",
  "background": {
    "telegramReading": false,
    "reflection": false,
    "personalChatMemory": false,
    "daytimeReflection": false,
    "deferredFacts": true,
    "kiraSelfEvolution": true,
    "kiraLife": false
  }
}
```

`normal` оставляет выбранный фон, `maximum` временно приостанавливает платный AI-фон. Отправляй только изменяемые поля: остальные предпочтения сохраняются. Все переключатели в одном запросе сохраняются атомарно; перезапуск и `Idempotency-Key` не нужны, повтор такого PATCH безопасен. Настройки действуют только для текущего аккаунта, общий кеш фоновых проверок обновляется сразу после записи, уже начатые циклы могут завершиться.

Доступные ключи:

| Ключ | Возможность |
| --- | --- |
| `telegramReading` | Общий переключатель автоматического чтения личного Telegram |
| `reflection` | Извлечение памяти из входящих сообщений |
| `personalChatMemory` | Изучение истории личных переписок |
| `daytimeReflection` | Дневные карточки по значимым событиям рефлексии |
| `inboxGuardian` | Вечерний обзор незакрытых вопросов в переписке |
| `dmReport` | Напоминания о непрочитанных |
| `chatGroupTracking` | Фоновое отслеживание групп |
| `chatPromptWatchers` | Наблюдение за чатами по сохранённым условиям |
| `deferredFacts` | Память из прямых разговоров с Кирой |
| `memoryConsolidation` | Упорядочивание памяти |
| `memoryInsight` | Самостоятельные подсказки из памяти |
| `kiraLife` | Кира пишет первой |
| `kiraInnerDevelopment` | Внутренняя жизнь и дневник персонажа |
| `kiraSelfEvolution` | Развитие характера из диалогов |
| `kiraLifeWebSearch` | Веб-проверка деталей самостоятельных событий |
| `recurringTasks` | Регулярные AI-задачи |
| `morningDigest` | Утренний дайджест |
| `morningDigestAi` | AI-приветствие в дайджесте |

Рефлексия по личным перепискам и память из прямого разговора — разные функции. Без Telegram доступны `deferredFacts`, память Киры, её самостоятельная жизнь и прочие функции, которым переписки не нужны. Включение `reflection` или `telegramReading` **не выдаёт доступ к аккаунту Telegram**: без личной сессии `effective` остаётся `false`. После подключения сессии для автоматического чтения явно включи `telegramReading` и нужные функции. Выключение `telegramReading` приостанавливает фоновое чтение, сохраняя ручные команды при наличии сессии; для полного отключения доступа используй `DELETE /account/telegram`.

## Личный Telegram

Для чтения личных переписок токена **бота** недостаточно. Необязательно подключи собственную авторизованную GramJS StringSession:

```json
{"apiId":12345,"apiHash":"<api_hash Telegram-приложения>","sessionString":"<личная StringSession>"}
```

Отправь её в `PUT /account/telegram`. Сервис проверит Telegram-личность сессии: она должна совпадать с подтверждённым владельцем бота. После сохранения runtime перезапустится; ответ `202 restarting`, затем ожидай `ready`. Получай StringSession на своём устройстве; API не принимает коды SMS или пароль Telegram. До подключения сессии чат, собственная память, напоминания и прочие функции бота работают, а доступ к личным перепискам недоступен.

`GET /account/telegram` возвращает только `{"personalSessionConfigured":true}` или `false`. `DELETE /account/telegram` удаляет credentials этого аккаунта и перезапускает его процесс; повтор удаления безопасен. После ответа доступ к личным перепискам прекращается, а бот и уже сохранённая память остаются. Этот запрос удаляет подключение из Киры; список авторизованных устройств самого Telegram управляется отдельно в Telegram.

## Резервирование и проверки

Резервируй служебную базу `KiraPlatform`, базы `kira_u_<uuid без дефисов>`, соответствующие PostgreSQL-роли, коллекции Qdrant, каталог аккаунтов и master key. Не копируй личную память оператора в новые аккаунты. Процессы изолируют состояние приложения; контейнер сервиса и его оператор остаются доверенной инфраструктурой.

`npm run test:accounts` проверяет регистрацию, вход, токены, привязку, изоляцию маршрутов, credentials и браузерную сеть. Интеграционный тест PostgreSQL включается только явным `KIRA_PLATFORM_TEST_PG_PORT` на одноразовом локальном PostgreSQL с тестовым паролем из файла теста; он не читает production `DB_*`.
