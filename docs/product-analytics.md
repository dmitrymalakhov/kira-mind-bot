# Пользовательская аналитика

В админке откройте **Аналитика**. Доступ защищён той же авторизацией, что настройки инстанса. Здесь доступны период 7/30/90 дней, канал Telegram/API, сценарий, цели продукта и ручная проверка последних результатов.

## Что считается пользой

Доставка ответа и `operationStatus: ok` — технические сигналы. Подтверждённая польза появляется только после положительной оценки пользователя или ручной проверки результата. Неоценённый результат остаётся неизвестным. Покрытие оценками и абсолютные размеры выборок показываются рядом с KPI.

Автоматические опросы полезности отключены: обычные, голосовые, проактивные и отложенные ответы Telegram и API не получают кнопки оценки; `/dialogue-jobs` не добавляет `feedback`. Доставка и технические исходы продолжают учитываться без изменения сообщения и рабочих кнопок. Старые кнопки и ранее выданные action tokens остаются совместимыми: оценки проходят прежнюю проверку подписи/срока/владельца через `/actions`, без требования совпадения с последним ходом. Неоценённые ответы по-прежнему не считаются подтверждённо полезными; ручная проверка доступна в админке.

Проактивные сообщения Kira Life и подсказки памяти также получают оценку. Доставка обычных напоминаний и регулярных результатов учитывается отдельно и может быть оценена в админке. Неподключённые к сбору обратной связи фоновые каналы не считаются измеренными; показатель проактивности относится к этим двум подключённым типам. Нет реакции — неизвестный исход.

## Определения

| Показатель | Определение |
|---|---|
| Пользователи с пользой за неделю | Уникальные пользователи с доставленным за последние 7 дней результатом, положительно оценённым пользователем/проверяющим. Каналы одного владельца объединяются. Учитывается подтверждённая польза по расписанию и от проактивности. |
| Активация за 24 часа | Доля зарегистрированных пользователей с подтверждённым первым результатом в первые 24 часа. Берётся завершившееся окно наблюдения: регистрации за выбранный период со сдвигом на сутки. |
| W4 Retention | Доля зарегистрированных пользователей с подтверждённой пользой в интервале `[регистрация + 21 день, регистрация + 28 дней)`. Для периода N дней берутся регистрации за N дней со сдвигом на 28 дней. |
| Подтверждённый успех | Положительно оценённые интерактивные обращения / все начатые обращения за период, включая неоценённые, ошибки и незавершённые. Это нижняя оценка успеха, зависящая от покрытия оценками. Отдельно показан успех среди оценённых. |
| Время до результата | p50/p90 от начала обращения до успешной доставки финального ответа. Уточнения и обязательный предварительный ответ исключены; корректность результата оценивается отдельно. |
| Время до первой пользы | p50/p90 от регистрации до первого подтверждённого результата среди достигших его пользователей. Рядом показано число оставшихся без подтверждённой пользы. |
| CSAT | Положительные пользовательские оценки / пользовательские оценки. Ручные проверки не подменяют мнение пользователя. |
| Исправления | Доля оценённых обращений, для которых зарегистрирована необходимость исправления. |
| Качество памяти | Явные оценки `memory_correct` / (`memory_correct` + `memory_wrong`). Это оценка проверенной выборки, а не автоматический recall всех сохранённых фактов. |
| Проактивность | Положительно оценённые проактивные сообщения / оценённые; рядом покрытие оценками. |
| Отказ от проактивности | Число пользователей, явно отключивших одну из функций сообщений в настройках за период. Повторное сохранение прежнего флага не создаёт событие. Фильтры канала/сценария на настройку аккаунта не применяются. |
| Ошибки доверия | Число результатов, по которым зарегистрирована ошибка доверия за период. Последующая положительная оценка не стирает зарегистрированный инцидент. Отсутствие зарегистрированных случаев не доказывает отсутствие ошибок. |

Текущая оценка каждого источника (`user`/`review`) выбирается из истории. Повторное нажатие не создаёт новую задачу и не увеличивает число успехов. При конфликте оценок результат не считается положительным. Продолжение подтверждённого runtime сохраняет исходный идентификатор и время начала; вспомогательное обращение исключается из знаменателя как `continuation`. Обычные новые запросы не наследуют идентификатор ожидающей задачи. Прямые команды без семантического результата отмечаются как доставленные, но их успешность остаётся неоценённой.

Когорты берутся из фактических регистраций платформы после включения сбора данных. В знаменателе остаются зарегистрированные аккаунты, которые ещё не подключили бота. Импортированные старые аккаунты и одиночный инстанс без регистрации участвуют в метриках использования и качества, но не выдаются за новых пользователей. Фильтр сценария/канала ограничивает полезные результаты, а не исходный состав когорты. До созревания когорт процент показывает «—».

Цели WVU, активации, W4 и подтверждённого успеха задаются оператором. Стартовые рабочие гипотезы пилота: **10 пользователей с пользой за неделю, активация 60%, W4 30%, подтверждённый успех 70%**. Это ориентиры продукта, а не отраслевые нормативы; их нужно пересмотреть после накопления данных. Кнопка «Подставить стартовые значения» заполняет черновик, а запись происходит только по «Сохранить». Чтение аналитики не меняет сохранённые цели, пользовательские значения и явно очищенные поля не заменяются стартовыми автоматически. Исторические события не создаются.

Рядом с фактом показывается **факт − цель**: для WVU в пользователях, для долей в процентных пунктах. Выполнение = факт / цель × 100%; при нулевой цели отношение не вычисляется, а абсолютное отклонение остаётся доступно. Для всех четырёх целей большее значение считается лучшим. При превышении цели процент выполнения может быть больше 100%, шкала визуально ограничена 100%.

До 20 наблюдений процентная метрика отмечается как предварительная. Для подтверждённого успеха также нужны 20 оценок и покрытие оценками не менее 80% всех начатых обращений: без этого низкое число подтверждений нельзя выдавать за проверенный провал качества. WVU ниже цели помечается предварительным в первую неполную неделю и при отсутствии оценок доставленных за неделю результатов. Эти пороги помогают читать дашборд, но не являются проверкой статистической значимости. При отсутствии зрелой когорты, неполной выборке или фильтре отдельного канала/сценария сравнение с общей целью отключается; цель остаётся видимой.

## Хранение и доступ

Runtime записывает дешёвые метаданные в PostgreSQL: `product_analytics_tasks`, `product_analytics_assessments`, `product_analytics_preferences`, `product_analytics_meta`. Тексты запросов/ответов, имена, Telegram ID, содержимое памяти и credentials в эти таблицы не записываются. Actor — хеш серверного tenant/instance + владельца; это псевдоним, а не анонимизация. Админский JSON не содержит actor. Опросы доступны только владельцу в личном канале. Ошибка аналитики не блокирует обычный ответ бота.

Платформа перед запуском worker выполняет ограниченную миграцию новых таблиц, включая импортированные БД с `KIRA_DATABASE_SYNC=false`, и выдаёт права только роли этого tenant. Остальная схема не синхронизируется. `kira_analytics_sources` хранит операторское соответствие аккаунта и БД без секретов. Admin backend читает только эти источники, агрегирует их по запросу UI и включает в когорты ещё не подключённые аккаунты. Клиент не может подставить произвольную БД.

При обычном одиночном запуске таблицы создаются во время инициализации runtime. Если отдельная установка использует роль без CREATE и без менеджера платформы, оператору необходимо вызвать `ensureProductAnalyticsSchema` из `admin-panel/productAnalyticsStore.js` с привилегированным подключением и выдать этой роли SELECT/INSERT/UPDATE на четыре таблицы. Не включайте полную синхронизацию схемы ради аналитики.

Агрегации работают в admin backend, а не в пользовательском ходе. На источник читается максимум 50 000 строк обращений в необходимом окне; при превышении лимита либо отсутствии таблиц источник помечается неполным, итоговые KPI скрываются. Неполная выборка не выдаётся за точный результат. История до включения слоя не восстанавливается из личных переписок. Автоматического TTL для аналитических таблиц пока нет.

Проверки: `tests/product-analytics.test.ts`, полный `npm test` и `npm run build:admin`. `node scripts/testProductAnalyticsPostgres.cjs` проверяет реальный PostgreSQL с текущим DB-подключением: создаёт отдельную временную БД, использует только синтетические события и удаляет эту тестовую БД в конце. Нужны операторские права CREATE DATABASE; рабочие диалоги и память не читаются.
