# Контекстный поиск по людям, связям и темам

Общий retrieval разбирает смысл запроса и сохраняет подтверждённый предмет поиска между репликами. Явные правила для короткой проверки связи остаются ускорением, а не единственным способом найти человека.

## План поиска и grounding

Существующий вызов `memoryExtraction` в `generateMemoryQueries` возвращает `MemoryQueryPlan`: прямые/фоновые фразы, самостоятельный поисковый вопрос, тип задачи (`identity/overview/relationship/specific`) и ссылки на людей/темы. Синонимы ролей интерпретируются этой же моделью; отдельный классификатор или новый провайдер не добавляются. Старый текстовый ANSWER/CONTEXT формат остаётся fallback.

Модель предлагает только поисковые ссылки. Она не выдаёт `person_id`, не создаёт личности и не подтверждает факты. `mention` должен встречаться в новом вопросе или в ограниченной истории. Связь от владельца должна происходить из текущих пользовательских слов; слова бота не создают такую связь.

`from=owner` с пустым `relationPath` обозначает самого аутентифицированного автора реплики. Дополнительно проверяется явная ссылка на себя (`я/меня/мой/моих` и другие формы) в дословном mention текущего вопроса. Это отличается от «увлечения моей жены», где путь `spouse_of` устанавливает другого субъекта. Предыдущий contact focus не подменяет явный запрос о себе. «Твои увлечения» не является ссылкой на владельца.

Новый runtime отправляет естественные вопросы сразу в canonical recall, без старого `maybeStartContactMemoryLookup`: тот считал «моих увлечениях» именем из двух слов и выдавал готовый отрицательный ответ до классификации и RAG. Legacy-path сохраняется, но отклоняет ссылки на себя; новый личный вопрос освобождает устаревшее pending contact clarification. Старые callback-и продолжают работать.

Разрешение человека использует scoped реестр `profile + ownerUserId`, сильный Telegram ID, подтверждённые aliases и существующие contact matching helpers. Два одинаковых имени не сливаются. Alias/время упоминания/долговременные записи при чтении не обновляются. Совпадение нескольких identities по одному сильному Telegram ID допускает единое read-only представление.

В recall допустим единственный компонент имени или фамилия в падеже. SQL ищет bounded candidates по displayName и aliases внутри profile/owner; отдельный read-only helper проверяет компонент, затем resolver проверяет единственность сильной identity-группы. Два однофамильца требуют уточнения. Если raw-страница достигла 12 кандидатов, уникальность не установлена даже при одном подходящем результате на этой странице. Action/contact persistence matching от этого не меняется.

`relationPath` содержит до трёх типизированных шагов по уже сохранённым evidence-backed edges. Направления `out/in` существенны; `either` допустимо только для симметричных типов. `parent_of`/`child_of` и `manager_of`/`reports_to` читаются также в обратном представлении. Семантические alternatives симметричного шага проверяются вместе: если они ведут к разным людям, результат остаётся неоднозначным. Вложенная роль проходит через промежуточного человека, а не заменяется собственной связью владельца. Недоказанный или неоднозначный путь не угадывается.

Query-time схема также учитывает подтипы: брак является частным случаем романтического партнёрства, поэтому поиск `partner_of` проверяет `spouse_of` даже если модель не перечислила альтернативу. Это чтение, не переписывание связи и не утверждение брака из слова «партнёр». Профессиональные связи отделены в инструкции планировщика; деловое партнёрство не должно преобразовываться в семейную роль. Разные подходящие endpoints сохраняют неоднозначность.

`relationPath` нужен для установления предмета вопроса, а не для ответа об отношениях. «Кто начальник Мирона Тестового?» требует перехода от Мирона к начальнику. «Что нас связывает с Мироном Тестовым?» использует named reference с дословным падежным `mention` и пустым путём: неизвестная связь не становится переходом к другому человеку. Тип `relationship` описывает историю взаимодействий, общие дела и темы общения; поисковые фразы не предполагают заранее конкретную работу или родство.

## Один факт и коллекции людей

`highlight` означает выбор одного конкретного факта из установленного профиля. До четырёх кандидатов проходят проверку субъекта, активного статуса, отрицания, confidence ≥ 0.7 и quality/inference-флагов. Embeddings и буквальный rerank по слову «интересный» не вызываются. Модель формулирует один факт по этой выборке; недостаток подходящих кандидатов не заменяется догадкой.

`people_list` содержит `peopleQuery.basis=relationships|communication|both` и до шести типизированных `relations` с направлениями. Корень — явная ссылка на владельца с пустым reference path; список другого человека не превращается в owner collection. `memoryPeopleRecall.ts` читает максимум 201 scoped identity, объединяя только одинаковый сильный Telegram ID. Имя не является ключом объединения.

Явная связь должна иметь owner endpoint, подходящий тип и направление, действующие даты/status, confidence ≥ 0.75 и не быть отрицанием. Для основания communication нужен contact-subject факт в выбранном домене, однозначная scoped identity с положительным Telegram contact ID и `sourceMessageIds` из прямого диалога `tg:<contactId>:...`. Простое упоминание в чужой переписке, групповой chat ID, имя в истории бота или наличие работы у человека этого не доказывают. Source-chat user записи не переатрибутируются.

`getPeopleMemories` фильтрует namespace/owner и contact/relation candidates; максимум три выбранных домена, scan budget 3000 raw points на выбранный домен или 500 при широком обходе. Приём ограничен одним evidence на человека/основание, чтобы сотни фактов первого собеседника не вытеснили остальных. Общий pool — 200 records, ответная коллекция — до 50 людей и 6500 символов. Контекст различает отношения и источники переписки, не объявляет список исчерпывающим и не выдаёт разговор о работе за трудоустройство в одной компании.

Коллекция сохраняется как topic focus без списка из первых четырёх людей. Она не задаёт адресата и не разрешает действия. `skills/people-and-memory/SKILL.md` направляет естественные вопросы в уже подготовленную память, а адресную книгу оставляет отдельным источником.

## Между репликами

`session.memoryRecallFocus` хранит проверенных людей, поисковую формулировку и memory IDs на 30 минут. Он привязан к владельцу и каналу; TTL, наличие доказательств и scope проверяются перед использованием. Это поисковый контекст, не `activePersonContext` и не разрешение на отправку сообщений, создание фактов или слияние людей.

После подтверждённой связи следующий вопрос «что про неё известно?» получает тот же entity scope. Явная другая тема/личность заменяет контекст. Единственное местоимение после обсуждения нескольких людей не выбирает одного по частоте.

Текущий структурированный reply с проверенным person/contact ID имеет приоритет над прежним поисковым focus. Его server-side контекст передаётся отдельно от пользовательского текста и не превращается в новые слова или факты пользователя.

Старые диалоги без нового focus восстанавливают поискового кандидата по сохранённым именам в ограниченной истории и реестру. История задаёт, о ком искать; её утверждения не попадают в фактическую выборку. Неразрешённый кандидат требует уточнения. Имена с обычной пунктуацией после них остаются распознаваемыми.

Foreground исключает из истории текущую реплику только если она действительно присутствует. В deferred snapshot текущего сообщения нет, поэтому последний предыдущий ответ сохраняется. Фоновая задача получает копию валидного focus, не живую session. Recurring-run очищает этот диалоговый контекст. Session storage сохраняет focus через перезапуск и конкурентное добавление истории.

## Чтение фактов

- Для выбранного человека scope применяется по сильному contact ID / stable person IDs; совпадающее имя другого ID не разрешает смешение. Общие факты владельца не подставляются вместо фактов человека. Bot/system/unknown evidence не становится его профилем.
- Owner overview использует `getOwnerMemories` с максимум тремя валидированными `domains` из плана (для всего профиля — все разделы). Пагинация выполняется по 50 записей, до 200 на домен и до 300 в conversational pool; namespace, owner, user-subject и expiry заданы в фильтре чтения. Это позволяет читать нужную тему, не теряя её за общим top-k. Граница сервиса — 400. Дополнительный общий owner scope требует явного user-subject, исключает чужие person/contact tags, bot/unknown и запрещённые источники из `isEligibleForUserSynthesis`. Наличие userId само по себе не доказывает, о ком запись. Старые смешанные source-chat записи не переатрибутируются.
- При переданном `acceptCandidate` лимиты 200 на домен / 300 общего conversational pool считают только допущенные записи. Отдельный scan budget составляет до 2000 raw points на выбранный owner domain, 500 на домен для широкого owner profile и 1000 для identity tags. Без фильтра прежние callers сохраняют границу 200 raw points. Повторные cursors, пустая страница и scan budget завершают чтение. Это устраняет ранний обрыв после неподходящих записей, но не обещает прочитать весь архив. Бот не получает неподтверждённые user-факты лишь ради наполнения ответа.
- Контекст явно обозначает owner как текущего пользователя и просит менять пользовательское «я/мои» на «ты/твои» в ответе. Собственные сведения ассистента и контактные факты остаются отдельными субъектами. Ограничения статусов и отрицаний сохраняются.
- `getMemoriesByTags` читает union identity tags страницами по 50 точек. Общий pool ограничен 300 записями в conversational caller, до 200 на домен; домены объединяются round-robin. Повторный cursor и недоступный домен не создают бесконечный обход. Namespace, owner и expiry проверяются на каждой странице. Это ограниченный pool, а не обещание прочитать весь архив.
- Для `overview` выбираются разные виды/домены сведений с приоритетом действующих устойчивых фактов и достоверности. Повторяющиеся рабочие записи не занимают всю выборку. Низкое качество и неоднозначное происхождение понижают приоритет и сохраняют оговорки. План, завершённое событие, отрицание и временные границы передаются явно. Компактный context ограничен 6500 символами; длинная запись является помеченным дословным фрагментом.
- Owner topic overview различает также сохранённые predicates внутри одного вида и домена: профессия, работодатель и навык не исчерпывают общий bucket из трёх фактов. Контекст просит сначала изложить конкретные сведения, затем уместные эпизоды, а неопределённость актуальности относить к конкретной детали. Старая запись не объявляется текущим составом команды или должностью.
- Продолжение обзора понижает приоритет уже показанных записей того же предмета поиска, чтобы «подробнее/ещё» находило дополнительные сведения. Сессия хранит не более 200 недавних memory IDs; это ограниченная история чтения, не журнал доказанного ответа и не бесконечный обход архива.
- Overview не вызывает embeddings и LLM-реранкер: после установленного человека нужны его сохранённые факты, а не семантическое совпадение с «неё». Финальный разговорный агент формулирует ответ по выборке.
- Для `specific` остаётся гибридный поиск и реранкинг внутри person scope. Вопрос для поиска/реранкера содержит только установленное имя и исходный запрос; выдуманное имя из model rewrite не задаёт личность. Для проектов/тем продолжение использует прежнюю поисковую формулировку без объявления новой личности.
- Отношения дополнительно читаются по `relation_subject_person_id` и `relation_object_person_id`: у записи может отсутствовать обычный identity tag второго участника. До двух union-пакетов по 16 tags и 100 записей дополняют основной pool; итог ограничен 400 уникальными записями. Scope проверяет оба сохранённых endpoints. Общего сканирования графа нет.
- `relationship` отдаёт приоритет сохранённым рёбрам запрошенной пары и тематическим фрагментам, сохраняя разнообразие видов и доменов. При одном человеке второй участник — владелец; при нескольких — другие запрошенные люди. В контексте `pair=queried` отделён от `pair=context`, отрицание/статусы/даты сохраняются. Обычный факт о человеке, источник чата и совпадение интересов не доказывают общую деятельность. Отсутствие структурированного ребра не отменяет явно описанного в дословном тексте взаимодействия. Embeddings и отдельный реранкер для этого обзора не вызываются.
- `memoryTask=lookup` в существующей intent-классификации оставляет фактические вопросы синхронными. Более глубокий анализ сохраняет прежний deferred маршрут. Валидный focus также не позволяет уверенной быстрой заготовке обойти поиск для продолжения.
- Skills runtime использует только канонически подготовленную память; старый дополнительный role-to-name resolver сохранён для legacy, чтобы новая модель не переопределяла установленную личность и не добавляла лишний AI-вызов.

## Проверки

`tests/memory-entity-recall.test.ts` покрывает semantic plan, ссылки, aliases/неоднозначность, scope/TTL, nested/directed paths, inverse predicates, topic changes, обзор и specific recall, пагинацию и восстановление старой истории. Дополнительные проверки находятся в `tests/fast-dialogue.test.ts` и `scripts/testSessionStorage.ts`.

Для реальной памяти replay блокирует provider/embedding/write методы и проверяет цепочку установления личности, чтение профиля и продолжение старой истории; выводятся только counts/flags. Отдельная модельная проверка использует синтетические вопросы, имена и проекты, после чего предложенный план может проверяться локально по связям без передачи найденных личных данных модели. Эти проверки не заменяют оценку качества итогового ответа на размеченных диалогах.

Поиск не восстанавливает отсутствующие в индексе сведения, не исправляет автоматически legacy-атрибуцию и не определяет единственного человека из нескольких подходящих endpoints без опоры. Массовое чтение архивов, переизвлечение фактов и смена embedding profile этой доработкой не запускаются.
