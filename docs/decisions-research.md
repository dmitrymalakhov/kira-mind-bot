# Исследование маршрутизации и Decisions API

Дата: 28 октября 2026 года. Приоритет пользователя: баланс, качество важнее небольшой разницы в задержке. Рабочие AI-настройки бота не менялись. На существующем шлюзе разрешён `/v1/decisions`, после чего выполнено живое сравнение.

Лучший измеренный кандидат для **узкого выбора MCP с приоритетом качества** — `gpt-6-luna`, `reasoning_effort=none`, короткий контракт JSON со списком сервисов, 512 output tokens. Decisions быстрее, но независимые ответы иногда противоречат друг другу. Лучший кандидат для **отдельного фильтра срочности** — один `predicate` Decisions с полной инструкцией и порогом 0,95: 32/32 в двух корзинах, p50=0,434 с против 1,260 с у JSON. Ни один результат не доказывает оптимальность для всего runtime.

После этого исследования в рабочей ветке реализован выбор MCP в существующем общем JSON-проходе. Фильтр рефлексии отдельно проверен на полном контракте жизненных событий: его итоговый порог **0,90**, а не предварительные 0,95 из узкой корзины срочности. Результаты внедрения и оставшиеся ошибки приведены ниже; они не подменяют исходные измерения.

## Что проверено

- 48 сценариев маршрутизации: чтение, изменения, несколько MCP, общие объяснения, память, отрицания, цитаты, продолжения, новая тема, публичный веб, будущие напоминания и недоступные действия.
- 16 сценариев триажа: срочные проблемы и обычные сообщения, старые события, повторное уведомление, исходящая реплика и инструкция внутри цитаты.
- Отдельные 16 сценариев маршрутизации для контроля первого этапа и ещё 16 новых сценариев триажа для второго этапа.
- Первый этап: 208 основных и 64 контрольных AI-вызова. После открытия Decisions: 288 сравнительных, 48 с согласованным выводом доступа и 176 контрольных. Итого **784 сравнительных обращения на 96 уникальных сценариях**, включая два неуспешных запроса. Пилоты и проверки endpoint в это число не входят.
- Только вымышленные запросы и четыре синтетических подключения: `market`, `warehouse`, `supplies`, `crm`. Личная память, реальные переписки, MCP-вызовы и отправка сообщений отсутствуют.

Запросы отправлялись через существующий OpenAI-клиент с адресом и ключом настроенного аккаунта. Диагностический процесс читал только AI-политику из БД в режиме read-only. Он не импортировал runtime бота и не записывал настройки, историю или квитанции.

Снимок действующей политики: классификация и быстрый диалог — `gpt-6-luna` / `none`; планировщик — `gpt-6-luna` / `low`, 4096 output tokens. Все эти маршруты имеют `allowFallback=false`. Поэтому текущий `classifyWithDecisions` откажется заменять закреплённую модель даже при включённом `KIRA_DECISIONS_ENABLED`. Нельзя обходить явный выбор пользователя простым снятием этого ограничения.

## Методика и границы сравнения

В основном наборе 24 calibration и 24 validation примера маршрутизации; для триажа — 8 и 8. Дополнительные 16 примеров маршрутизации не участвовали в первом основном прогоне, затем повторно использовались для контроля Decisions. Они уже были известны исследователю ко второму этапу, поэтому это повторная проверка, а не полностью слепой тест нового дизайна. Ещё 16 примеров триажа добавлены перед финальным контролем. Пороги зафиксированы до этого контроля и по его результатам не менялись.

В каждом запуске — один ответ на пример и конфигурацию, concurrency=2, порядок конфигураций чередуется, автоматические retries отключены. Есть повторные измерения некоторых конфигураций между этапами, но систематических повторов для оценки дисперсии и доверительных интервалов нет. Порог выбран на маленькой calibration-корзине, а не доказан как универсальный.

Проверяются `mcpAccess`, `memoryTask`, `mcpAllowWeb`, а для специализированных кандидатов — ещё точный набор ID сервисов. **Полный классификатор и быстрый диалог не возвращают этот набор**, его отсутствие у них не считается ошибкой: сервисы выбирает следующий планировщик.

Обычный и быстрый классификаторы используют актуальные инструкции рабочей копии проекта. Для быстрого варианта подставлена вымышленная краткая персона. Специализированный JSON-контракт возвращает только четыре перечисленных поля; он не извлекает сроки, адресатов, группы чатов, subIntents и остальные поля общего классификатора.

Основная метрика — совпадение полей с ручной разметкой. Дополнительно показывается эффективная точность: `mcpAllowWeb=true` при одновременно `mcpAccess=none` не меняет маршрут и не даёт прав, хотя нарушает контракт. Исходная ошибка сохраняется в сырых результатах. При наличии MCP проверка этого флага остаётся строгой.

Это микробенчмарк маршрутизации. Он не измеряет весь ответ, качество извлечения аргументов, исполнение инструментов, память, подтверждения, работу с реальным каталогом всех подключений или итоговую полезность текста. Успех здесь не доказывает правильность всей цепочки.

## Первый этап: 48 запросов маршрутизации

Все задержки относятся к одному вызову API, в секундах.

| Конфигурация | Совпали общие поля | Эффективный маршрут | Точный набор MCP | p50 | p95 | Output tokens, всего |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Общий классификатор, `none`, 1536 | 46/48 | 46/48 | Не измеряется | 1,920 | 2,607 | 4931 |
| Быстрый диалог, `none`, 1536 | 44/48 | 44/48 | Не измеряется | 2,338 | 2,922 | 5652 |
| Короткий выбор MCP, `none`, 512 | 46/48 | **48/48** | **48/48** | **1,262** | **2,447** | **1418** |
| Тот же короткий контракт, `low`, 1024 | 45/48 | 45/48 | 48/48 | 1,826 | 4,164 | 3518 |

Средний вход: около 2451 токена у общего классификатора, 2866 у быстрого диалога и 499 у коротких вариантов. У длинных запросов были реальные cache hits; у коротких — нет. Поэтому пятикратное уменьшение входа не означает пятикратное уменьшение цены.

У общего классификатора два расхождения относятся к вопросу о каталоге и поручению недоступной торговли. При вопросе с буквальным «MCP» существующий deterministic guard всё равно запускает инструменты. Для запрещённой торговли допустим безопасный отказ без вызова сервера; строгая разметка ожидала распознавание порученного изменения. Это расхождения полей, а не доказанные ошибки пользовательского ответа или выполненные сделки.

Быстрый диалог дополнительно потерял `write` в двух просьбах создать обращение, в том числе после чтения другого MCP. У варианта `low` возникли три ложных MCP-маршрута: неподключённый календарь и два напоминания о будущем; два из них ошибочно получили `write`. Усиление reasoning само по себе не исправило контракт.

Короткий `none` ошибочно выставил `mcpAllowWeb=true` в двух запросах исключительно публичного веба при `mcpAccess=none`. На фактическую маршрутизацию этих запросов флаг не влияет. Перед использованием такого кандидата результат всё равно нужно валидировать и нормализовать.

## Контроль первого этапа: 16 новых запросов

| Конфигурация | Совпали общие поля | Точный набор MCP | p50 | p95 |
| --- | ---: | ---: | ---: | ---: |
| Быстрый диалог, прежние инструкции | 15/16 | Не измеряется | 2,403 | 3,771 |
| Пробная переформулировка инструкции (`fast-fixed`) | 13/16 | Не измеряется | 2,517 | 3,767 |
| Короткий выбор MCP, `none` | **16/16** | **16/16** | **1,306** | **2,062** |
| Короткий выбор MCP, `low` | 15/16 | 16/16 | 1,968 | 4,977 |

Пробная формулировка явно разделяла чтение и изменение, но три просьбы создать обращения всё равно потеряли `write`. Она отклонена и не перенесена в runtime. У `low` снова возник ложный `write` для просьбы поставить напоминание. Увеличение модели или добавление ещё одной похожей фразы нельзя считать исправлением без нового независимого прогона.

Итого у короткого `none` точный набор сервисов совпал на 64/64 запросах двух прогонов. Это результат небольшой синтетической выборки, не гарантия для реальных сообщений.

## Триаж первого этапа

Короткий JSON-предикат на `gpt-6-luna`, `none`, лимит 512: 16/16, p50=1,269 с, p95=2,108 с. Ложных уведомлений и пропусков в этой корзине нет.

Этот набор оценивает срочность уведомления, а не весь контракт рефлексии. В `services/reflectionModeService.ts:triageForHighPriority` уже есть отдельный вызов с единственным полем `urgent`: это подходящая точка для исследования замены на Decisions без дополнительного AI-шага. Перед заменой нужно расширить корзину жизненными событиями, отношениями и критериями действующего фильтра. Измеренная здесь точность не переносится автоматически на эти классы.

Детерминированные проверки направления, возраста и повторного уведомления стоит выполнять до платного AI-вызова, когда эти метаданные уже известны.

## Второй этап: живое сравнение Decisions

Изначально шлюз отвечал `403 endpoint_not_allowed`. По разрешению пользователя через уже доступный SSH добавлен только точный путь `/v1/decisions` в `ALLOWED_PATHS`. Шлюз перезапущен и остался активным; запросы без ключа к `/v1/models` и `/v1/decisions` по-прежнему получают `401`. Исходный файл настроек сохранён на сервере для отката. Другие пути, ключи, провайдер, ограничения и AI-политика Киры не менялись. Доступ с текущего компьютера оказался достаточным, переход на MacBook Pro не понадобился.

Сравнивались семь вопросов: доступ MCP, память, дополнительный веб и четыре сервиса. Для каждого сервиса — либо `predicate`, либо `choice` из `unused/read/write`; это позволяет выбрать несколько MCP. Варианты `lean` сокращают повторение общих правил в вопросах. В пилоте инструкция триажа без явной формулировки утверждения дала ложную тревогу на благодарность; до сравнительного прогона вопрос исправлен. Пилот исключён из таблиц.

| Короткий JSON `none` | 46/48 | **48/48** | **48/48** | 48/48 | 1,369 | 2,134 |
| Decisions `predicate` | 45/48 | 45/48 | 47/48 | 48/48 | 0,560 | 0,776 |
| Decisions `choice` | 45/48 | 45/48 | 48/48 | 48/48 | 0,561 | 0,655 |

Типичная ошибка независимых вопросов: `mcpAccess=read`, но список сервисов пуст, когда пользователь вспоминает личный разговор или спрашивает неподключённый календарь. Упоминание товара из уже показанного диалога также ошибочно превращалось в поиск долговременной памяти. Высокая точность списка сервисов сама по себе недостаточна для корректного маршрута.

У `derived-choice` тоже семь вопросов: вместо отдельного доступа добавлен признак просмотра каталога, уточнено отличие долговременной памяти от текущей истории. `mcpAccess` выводится кодом из ролей выбранных сервисов и признака каталога. Это устраняет часть противоречий, но один смешанный запрос потерял `memoryTask=lookup`. Ещё два обращения завершились `503`, без повторов. Ошибки запросов включены в знаменатели точности; среди 46 полученных ответов общие поля верны у 45, набор сервисов — у всех 46. По одному запуску нельзя приписать сбои именно этому варианту API или инструкции.

### Выбор порогов и контроль

Сетка: 0,50 / 0,65 / 0,80 / 0,90 / 0,95. Выбор — только по calibration; для триажа цена ложного уведомления 5, пропуска 2, для маршрутизации — число неверных полей плюс штраф 10 за ложный `write`. При равенстве выбран больший порог. Это исследовательская функция потерь, не согласованная продуктовая политика уведомлений.

| Конфигурация | Порог маршрутизации | Calibration: верно | Validation: верно |
| --- | ---: | ---: | ---: |
| `predicate` | 0,95 | 22/24 | 23/24 |
| `choice` | 0,95 | 22/24 | 23/24 |
| `lean-predicate` | 0,95 | 23/24 | 22/24 |
| `lean-choice` | 0,90 | 23/24 | 22/24 |
| `derived-choice` | 0,90 | 23/24 | 22/24, включая два `503` |

Порог применяется к предикатам и вероятности использования сервиса; категориальные `mcp_access` и `memory_task` берутся из выбранного ответа. Он не исправляет их неправильный выбор. В threshold sweep строки без вероятностей не участвуют; поэтому для `derived-choice` отдельно учитываются две ошибки запросов, а не показывается вводящее в заблуждение 22/22.

## Возможности и ограничения Decisions

Официальный API поддерживает `predicate`, `choice`, `score`; независимые вопросы можно объединять. Сейчас поддерживается `gpt-6-luna`; для Decisions вывод не тарифицируется, базовый некешированный вход — $0,10/1M. Для произвольных аргументов и текста нужны генеративные API. [Руководство Decisions](https://developers.openai.com/api/docs/guides/decisions).

В этом исследовании проверен `input_json` на существующем шлюзе. Старые 143 мс из диагностики относятся к отказу шлюза, а не к работе модели. Измеренное ускорение одного фильтра не равно ускорению всего ответа бота. Вероятности нельзя считать гарантированно откалиброванными: пороги следует проверять на своём контракте. [Формат запроса](https://developers.openai.com/api/reference/resources/decisions/methods/create), [ограничения и вероятности](https://developers.openai.com/api/docs/guides/decisions).

Текущий адаптер `ai/decisionRouting.ts` задаёт другой, более широкий контракт классификации. Результаты семи исследовательских вопросов нельзя переносить на него автоматически. При отказе, ошибке API, неполном или неизвестном ответе нужен существующий разрешённый маршрут; результаты модели не заменяют allowlist и подтверждения изменений.

## Рекомендуемые конфигурации

| Область | Решение сейчас | Что проверять следующим |
| --- | --- | --- |
| Самодостаточный диалог | Сохранить совместный `fastDialogue`, Luna `none`, 1536 | Не добавлять отдельный роутер перед каждой бытовой репликой |
| Выбор MCP | Встроен список нескольких проверенных ID в текущий JSON-проход; Luna `none`, прежний лимит 1536 | Сохранены остальные поля классификации; узкий эксперимент с 512 не подменяет общий контракт |
| Планирование вызовов | Сохранить действующий Luna `low`, 4096 | Отдельный end-to-end eval планов, аргументов, отказов и числа раундов; здесь модели планирования не сравнивались |
| Отдельный фоновый фильтр | Для полного контракта рефлексии: один `predicate`, порог 0,90, только на уже выбранной OpenAI Luna | Реализована замена прежнего булевого вызова с возвратом к JSON при ошибке; остальные модели сохраняют JSON |
| Decisions для MCP | Сохранить исследовательским кандидатом: `derived-choice`, порог 0,90, согласованный вывод доступа | Нужны более широкая независимая корзина, обработка сбоев и явный выбор endpoint в AI-политике; не снимать `allowFallback=false` ради обхода |

Дополнительный последовательный вызов короткого роутера добавляет примерно измеренное время одного API-вызова. Переход с 2,3 с на отдельные 1,3 с не является ускорением, если вслед за ними всё равно выполняется прежний вызов. Оптимизировать нужно сумму вызовов и долю ненужных веток.

Для автоматического выбора MCP достаточно локального каталога разрешённых возможностей в существующей классификации, затем загрузки схем выбранных инструментов и планирования. Независимые чтения разных MCP можно выполнять параллельно; чтение, которому нужны SKU из предыдущего результата, планируется после получения этих SKU. Специализированный роутер даёт лишь выбор источников; он не выстраивает аргументы этой цепочки.

## Проверка реализации после исследования

В общий JSON-формат включены поля `mcpAccess=none|read|write`, `mcpServers` и `mcpAllowWeb`. В fastDialogue больше нет второй конкурирующей инструкции о чтении/вебе. Нормализация отбрасывает неизвестные ID, убирает дубликаты, объединяет источники составных частей и не выводит право на изменение из одного списка серверов. При MCP черновой быстрый ответ заменяется маршрутом инструментов. Кеш зависит от каталога; старые результаты без списка остаются совместимы с discovery.

Планировщик видит проверенные ID и может сразу читать схемы нескольких сервисов. При пустом или недостаточном выборе сохраняется `mcp.listServers`. Интеграционный тест проходит реальные классификацию, упаковку плана, MCP-сервис и ядро со сценарными ответами моделей: получает фактический SKU из склада, передаёт его сервису поставок и сохраняет источники обоих результатов. Это проверка исполнения с тестовыми ответами моделей, а не живой замер качества AI-плана.

### Полный контракт рефлексии

Отдельная новая корзина: 32 основных примера (16 calibration, 16 validation) и 16 контрольных. В каждом разбиении поровну положительных/отрицательных примеров. Помимо срочных просьб проверяются увольнение, смена работы, переезд, свадьба, развод, диагноз, рождение ребёнка, конфликт и изменение отношений; отрицательные примеры включают вымысел, цитаты, общие вопросы, рекламу и давние разрешённые события.

Сначала применён предварительный порог 0,95. В calibration он пропустил одно изменение договорённости. По заранее заданной сетке лучший консервативный порог без ошибок calibration — **0,90**. Он зафиксирован до просмотра контрольных ответов. API не получает порог: сырые вероятности первой серии, записанные с нормализацией 0,95, пересчитаны кодом по зафиксированным 0,90; исходный NDJSON не переписан.

| --- | ---: | ---: | ---: | ---: | ---: |

Реализация использует Decisions лишь если выбранный `lightweightText` уже равен OpenAI `gpt-6-luna`, включая закреплённую модель, с reasoning `none` или без явного уровня; другой провайдер, модель или заданный уровень reasoning не подменяются. При отказе/неверном ответе/ошибке endpoint выполняется настроенный JSON-вызов. Обычный таймер анализа сохраняется при любом сбое.

Исходящие и пересланные сообщения, а также сообщения старше 30 минут остаются контекстом, но не запускают срочный triage и не расходуют его cooldown. После ответа AI проверяется, что исходный буфер ещё существует и рефлексия включена. ## Воспроизведение

Исходники: `scripts/researchDecisions.cjs`, `scripts/lib/decisionResearch.js`, `scripts/lib/decisionResearchRunner.cjs`. Набор не пополняют из production-истории. Границы исследования и scoring проверяются `tests/decisions-research.test.ts`.

Сначала собрать TypeScript, чтобы standalone инструкции соответствовали рабочему коду:

```bash
npm run build:server
npm run eval:decisions -- --bundle /tmp/kira-decisions-study.cjs \
  --variants current-json,fast-current,compact-none,compact-low
```

Выполнить в локальном account-контейнере своего Compose project; stdout сохранить в ignored каталог с закрытыми правами:

```bash
mkdir -p runtime-data/diagnostics/decisions-research
umask 077
docker exec -i <account-container> node - < /tmp/kira-decisions-study.cjs \
  > runtime-data/diagnostics/decisions-research/run.ndjson
npm run eval:decisions -- --summarize runtime-data/diagnostics/decisions-research/run.ndjson
```

Для Decisions выбрать `--variants decisions-predicate,decisions-choice,decisions-lean-predicate,decisions-lean-choice`. Для согласованного доступа отдельный запуск `--variants decisions-derived-choice`. По одному probe на API; недоступный endpoint исключается из запуска, без обращения к нему для каждого примера. Раннер не меняет рабочий флаг Decisions и не использует runtime fallback.

`--summarize` выводит выбранные только по calibration пороги и отдельные validation-метрики. Перед контролем сохранить карту порогов в JSON вида `{"decisions-predicate":{"routing":0.95,"triage":0.95}}` и передать `--thresholds /tmp/frozen-thresholds.json`. `--heldout` включает контрольную маршрутизацию, `--heldout-triage` — её и новые 16 примеров триажа. `--ids a,b` ограничивает примеры. `--repeats 1..3` позволяет оценить разброс в пределах 350 вызовов; при превышении лимита запуск отклоняется. `fast-fixed` — только отклонённый эксперимент, не исправленная production-конфигурация.

Для реализации: `--integrated-mcp --variants current-json,fast-current` проверяет широкий JSON-контракт и нормализацию списка MCP; добавление `--integration-control` выбирает новые контрольные примеры. `--reflection-triage` использует полный чистый контракт из `ai/reflectionTriagePolicy.ts`, а `--heldout` вместе с ним — контроль рефлексии. Сборка диагностического бандла не загружает конфигурацию или персонажа бота; тест бандла отдельно проверяет перенос скомпилированных helper-ов. Для точного повторения старого `fast-fixed` нужен его сохранённый бандл: текущий fastDialogue уже изменён.

Полные NDJSON и агрегаты оставлены локально в `runtime-data/diagnostics/decisions-research-20261028-glgV6R/`. Изменения последующей отчётности не подменяют исходные ответы и сырые ошибки.
