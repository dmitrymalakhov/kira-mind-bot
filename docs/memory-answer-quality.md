# От найденной памяти до содержательного ответа

Попадание записи в RAG-контекст не доказывает, что ответ пользователю использовал её правильно. Поиск и синтез проверяются отдельно.

## Общий путь

1. Семантический план устанавливает вид вопроса, ссылки, темы и необходимость контекста переписок. Модель не назначает личности и не подтверждает факты.
2. Scoped resolver и существующие фильтры допускают evidence; topic facets сохраняются в owner/channel-bound focus. Продолжение может использовать прежний subject даже при reference `kind=topic`. Новый явно названный предмет не наследует прежние facets.
3. Retrieval возвращает текст, ссылки на показанные записи и `MemoryRecallSummary`: `found/empty/ambiguous/unresolved/unavailable`, subjects, domains и число evidence. Пустота поиска и неоднозначность — разные результаты.
4. Метаданные проходят foreground, deferred jobs, kernel и инструмент `memory.search` до `conversationAgent`. При смене результата инструмента обновляется и summary.
5. Personal lookup использует `MEMORY_ANSWER_RULES` и `buildMemoryAnswerPrompt`. В них нет биографии/настроения/self-events Киры и не добавляется dialogueSummary после свидетельств. Короткая история обозначена только контекстом ссылок. Прежнее «не знаю» ассистента не отменяет факты.

Обзор раскрывает разные конкретные аспекты; точный вопрос отвечает точно; интересный факт выбирает один; коллекция перечисляет найденных людей. Прошлое излагается как прошлое, отрицание и запланированный статус сохраняются. Недоказанное текущее состояние не подменяется уверенным утверждением и не становится поводом отказаться от всего ответа. Lookup не вызывает self-evolution и не превращает ответ о пользователе в событие жизни персонажа. Свободный Telegram-ответ остаётся обычным текстом без Markdown.

## Контекст переписок

Для широкого owner overview деятельности/проектов semantic plan может вернуть `includeConversations=true`. Допуск требует одного установленного owner subject и выбранных domains. Личные предпочтения, здоровье, точные факты и профиль другого человека такого расширения не требуют.

Используется существующий `recallMemoryPeople`: scoped directory, положительный contact ID, matching direct `tg:<peer>:<positive-message>` sources, contact subject, domain и quality checks. Добавляется до шести фрагментов из разных собеседников отдельным блоком (до 1800 символов). Он уменьшает бюджет основного блока; суммарно остаётся 6500 символов. Embeddings, reranker и дополнительный AI-review не вызываются.

Эти записи не включаются в owner fact pool. Переписка и её тема не доказывают автора проекта, работодателя или роль собеседника. Синтез должен сохранять исходного субъекта. Расширение не переатрибутирует legacy source-chat записи и не меняет storage.

## Проверка

`tests/memory-answer.test.ts` проверяет scoped retrieval → настоящее kernel → настоящий conversationAgent, подменяя только внешнюю модель. Проверяется, что все выбранные сведения и outcome доходят до финального вызова, а self-memory/устаревшая сводка не вмешиваются. Есть регрессии topic continuation, смены темы, атрибуции и отдельного conversation context.

`scripts/fixtures/memory-answer.synthetic.ts` содержит только вымышленные примеры: обзор работы и профиля, собственные увлечения, совместные дела, прошлое, отрицание/план, интересный факт, неоднозначность, пустая выборка, инструкция внутри источника и сохранение субъекта переписки.

Опциональный live eval в настроенном диагностическом runtime:

```sh
npm run eval:memory:answers -- --live
```

Он использует обычную model policy и реальный путь `runKiraRuntime → conversationAgent`, с готовыми синтетическими evidence packets. БД открывается read-only, schema synchronization отключена; реальная память и история не читаются, Telegram transport не вызывается. `--answers` показывает только ответы на вымышленные примеры. Для уже инициализированной read-only диагностики доступен экспорт `runMemoryAnswerEval`.

Проверки оценивают покрытие требуемых содержательных аспектов и запрещённые утверждения, а не только наличие ответа или evidence IDs. Это ограниченный регрессионный набор, не оценка всей production-памяти и не независимая экспертиза каждого утверждения. Реальный архив по умолчанию проверяется локальным read-only replay без провайдеров, записи и отправки сообщений.

## Приватная корзина реальных вопросов

Владелец может отдельно разрешить полный прогон через конкретный настроенный API с вопросами, тестовой историей и ограниченными релевантными фрагментами своего архива. Согласие на чтение базы само по себе не заменяет разрешение на такую передачу. Файлы корзины, исходные факты, ответы, планы, trace и оценки сохраняются только в ignored `runtime-data`, с ограниченным доступом; реальные примеры не копируются в код, fixtures и документацию.

Прогон использует реальный `processMessage`, текущую model policy и scoped Qdrant namespace. Для проверки обычного Telegram-входа задаётся `dialogueTurnId`, иначе измеряется только путь intent classification, без `fastDialogue`. Сессии тестовых цепочек изолированы от живого диалога. SQL открывается с `default_transaction_read_only=on`, schema synchronization выключена; memory mutations, access reinforcement, session persistence, self-evolution и Telegram transport блокируются. Постановка фонового job подменяется локальной квитанцией и учитывается отдельно. Отсутствие исключений не заменяет проверку счётчиков заблокированных операций.

Нужно записывать не только кандидатов retrieval, но и фактический context/summary конечного `conversationAgent`: повторный инструмент может потерять или заменить первоначальную выдачу. Проверка `scripts/memoryEvaluation.ts` независимо оценивает маршрут, число уникальных доказательств, установленного субъекта, сохранение известного identity proof и наличие новых записей при доступном продолжении. Оценка моделью дополнительно проверяет содержательность, неподтверждённые утверждения и повторы. Её вердикт требует сверки со структурными свидетельствами: модель может принять честный отказ при сбое поиска или неверно прочитать направление связи. Результаты этих слоёв показываются раздельно.

## Сохранение результата до ответа

- Abstention `НЕОПРЕДЕЛЕНО` не конкурирует с понятным личным вопросом; близкие реальные действия сохраняют уточнение.
- Смысловой lookup не запускает планировщик повторно из-за слов «задачи» или «напиши». Инструменты настоящих действий и составные запросы продолжают работать.
- Указательное «этого человека» использует установленный focus. Типизированный путь, установивший личность, сохраняет собственное доказательство независимо от guessed domain.
- Для точного identity-вопроса scoped typed-relation resolver выставляет `identityVerified` только при одном установленном endpoint и показанных доказательствах. Конечный слой возвращает проверенное имя без нового модельного вызова. Произвольный summary или модельный план не выставляет этот флаг; неоднозначность и отсутствие evidence не допускают короткого ответа. Вопрос «что помнишь о близком человеке» проходит полный overview, а не этот shortcut.
- Для отношений `conversation=owner_direct` отмечает проверенный прямой источник; `not_proven` не доказывает обсуждение владельца с человеком. Ни одна метка не меняет субъекта действия.
- Продолжение обзора предпочитает ещё не показанные записи. `freshEvidenceCount=0` и `noNewEvidenceInPool=true` означают исчерпание только текущего ограниченного пула. Повторный запрос новых фактов не получает старый пакет заново; явное пояснение прежних деталей сохраняет доступ к нему.
- При сборке обзора конкретные записи идут перед производными chapter/episode/user-schema. Частые слова вопроса в длинной сводке не должны вытеснять первичную личную подробность из бюджета. На продолжении приоритет ещё не показанного свидетельства сохраняется, включая новые сводки; specific ranking не меняется.
