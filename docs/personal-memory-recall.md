# Поиск личных фактов и связей

Прямой lookup ниже — быстрый частный путь. Синонимы, вложенные роли и продолжения вопросов обрабатывает [общий контекстный поиск](entity-aware-memory-recall.md). Подтверждённый прямой результат сохраняет grounded focus для следующей реплики.

Короткий вопрос об имени близкого человека или месте работы — запрос к сохранённым сведениям. Он получает синхронный поиск и полный ответ, а не автоматическое обещание фонового исследования. Неправильное `memoryNeed=none` от классификатора не должно отключать поиск для такого вопроса.

## Единая подготовка

`fetchAgentMemoryContext` используется обычным обработчиком и `dialogueJobs.deepen`. Перед общим multi-query recall он проверяет явную роль владельца («моя жена», «мой коллега» и падежные формы):

1. Читает сохранённые `person_relation/relation_type` записи в namespace бота и user scope.
2. Принимает только действующие, неотрицательные свидетельства с endpoint `user` и другим `person_id`. Не считает bot/system/unknown свидетельством личной связи.
3. Читает реестр людей по точному ID, профилю и владельцу. Старый и новый ID считаются одним человеком только при одинаковом сильном Telegram ID. Совпадение имени не разрешает объединение.
4. Безымянная роль («жена») не становится отдельным кандидатом на имя. Противоречивые сильные ID, ссылка на самого владельца и несколько реально различных людей не разрешаются по частоте или cosine score.
5. Подтверждённый результат включается отдельным блоком доказательств с memory IDs. Reranker и общий token budget не могут выбросить его до передачи в синтез. Точный вопрос с установленным именем обходится без генерации поисковых запросов и reranker.

Проверка явных семейных ролей относится к целевому именованному endpoint. «Владелец является мужем Лады Тестовой» и «Лада Тестовая называет владельца своим мужем» не говорят, что Лада — муж: слово описывает владельца. Напротив, «Муж владельца — Мирон Учебный» прямо определяет роль Мирона и не отвечает на запрос о жене. При неустановленной текстовой привязке роль не выводится из имени, а разные подходящие endpoints остаются неоднозначными.

Короткая смена родственника сохраняет вид сведений из предыдущего пользовательского вопроса: имя остаётся именем, обзор — обзором, место работы — местом работы. Корень owner/named также сохраняется; прежний найденный родственник не становится корнем новой связи автоматически. Явное «его/её» может задать вложенный путь от прежнего focus. Эти решения входят в существующий семантический план; источник и личность по-прежнему подтверждаются сохранёнными свидетельствами. История и новая реплика стоят в конце инструкции query-generation, рядом с заданием восстановить текущую просьбу. Для named-reference mention содержит имя корня, для owner/focus — дословную роль или местоимение. Направление асимметричного пути следует субъекту и объекту типа; симметричный тип resolver читает с обоих концов даже при ошибочном out/in модели.

Модуль читает уже существующие связи. Он не создаёт личности, не сливает старые записи и не меняет историю. При отсутствии однозначной опоры работает общий гибридный поиск. Контактные ограничения остального retrieval сохраняются: вопрос о жене другого человека не разрешает читать связи владельца как ответ.

## Общий поиск

Для вопроса о работе добавляются детерминированные формулировки («работаю», «работает», «работодатель», «место работы»), чтобы поиск не зависел только от буквального текста вопроса и решения LLM. Для русских слов родства используются Unicode-границы, а не ASCII `\b`. Общий hybrid recall, исправления отбора кандидатов и реранкинга описаны в [карте pipeline](memory-retrieval-pipeline.md); схема embedding сохраняется.

Отсутствие найденного факта не доказывает, что пользователь никогда его не сообщал. Ответ должен обозначать ограничение текущего поиска, а не утверждать «ты не называл». Роль не является именем и не принимается как `third_party.targetName` при новых записях.

Точные бытовые реплики вроде «с работы пришёл» остаются разговором. Их нельзя автоматически превращать в поиск работодателя, self-memory или фоновую задачу. Составные просьбы, вопросы, reply/forward и pending-state сохраняют каноническую обработку.

## Проверка

`tests/personal-recall.test.ts` и `tests/fast-dialogue.test.ts` проверяют прямые/обратные связи, падежи, неоднозначность, совпадения имён, старые ID, безымянные роли, срок действия, отрицание, owner scope, защищённый от reranker контекст и синхронный ответ. Fixtures полностью синтетические.

Проверка production проводится отдельным read-only replay: сравниваются наличие сохранённого человека и имени в итоговом контексте, число чтений, отсутствие model calls и записей. Тексты памяти, реальные имена и credentials не переносятся в код, тесты или отчёты. Количество файлов и объём на диске не равны числу доступных индексированных фактов: полнота импорта проверяется отдельно от качества retrieval.
