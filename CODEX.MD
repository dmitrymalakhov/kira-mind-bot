# CODEX

## Назначение файла
- `AGENTS.md` в корне — кросс-платформенная точка входа для coding agents; он должен отправлять агент к `CODEX-RULES.MD` и `CODEX.MD`.
- `CODEX-RULES.MD` в корне хранит обязательные правила репозитория и имеет более высокий приоритет, чем остальные локальные markdown-файлы.
- `CODEX.MD` в корне проекта хранит локальный инженерный контекст именно для `kira-mind-bot`.
- Глобальный `../CODEX.MD` не редактируется для проектных деталей, которые относятся только к этому репозиторию.

## Архитектурные решения

- Фильтр семейной роли проверяет явное определение роли целевого именованного endpoint, а не наличие слова о другом участнике в общем тексте. При параллельной смене роли semantic query-generation сохраняет вид искомого сведения и исходный owner/named-корень; focus становится корнем вложенной связи только при явной ссылке на прежнего человека. История и новая реплика располагаются рядом с итоговым заданием существующего вызова, без отдельного AI-router и новых разрешений.
- Производные главы/модели/индексы заменяются сохранением всего нового набора перед удалением прежнего snapshot; неподтверждённый save не разрешает удаление. Компрессия сохраняет первичные факты. Source IDs главы/модели должны происходить из показанного пула и не подставляются случайным fallback. `getRecentMemories` сортирует timestamp в Qdrant до top-k с datetime-индексом; первая страница ID не является недавней памятью. Карта найденных проблем и следующие этапы: docs/memory-audit-2026-10-29.md.
- Пользовательская аналитика отделяет техническую доставку от подтверждённой пользы. Runtime пишет только метаданные и явные оценки без текстов/Telegram ID; агрегации и цели находятся в admin backend. Неоценённое не считается успешным, регистрации до включения слоя и импортированные аккаунты не становятся новыми когортами. Уточнения и отложенные ответы сохраняют analyticsTaskId исходной задачи. Привилегированную миграцию новых таблиц импортированных tenant-БД выполняет менеджер платформы без включения полного synchronize. См. docs/product-analytics.md.

- Контактные данные профиля Telegram отделены от recall переписки: существующая классификация возвращает `telegramProfile`, который открывает read-only `contacts.getProfile` до разговорного ответа. Живое чтение использует общий identity resolver с явным набором кандидатов, не LLM-выбор fuzzy top-k. Пустая память не отменяет проверку профиля; тёзки/неполная страница не доказывают личность, а отсутствие phone в свежем профиле не заменяется кешем. Доступ остаётся только у владельца в личном канале, без чтения сообщений или сохранения новых фактов.
- Только read-only lookup профиля нормализует косметические emoji/невидимые символы во всём наборе кандидатов до проверки уникальности; исходные display names и ID сохраняются. Эта нормализация не расширяет правила записи, отправки и слияния людей.
- Незавершённое разрешение прямой связи от владельца допускает ограниченное чтение его собственных текстовых фактов: отсутствие канонического ребра не доказывает отсутствие ответа. Это не устанавливает person_id/focus и не разрешает действия с человеком; чужие, истёкшие и неоднозначные свидетельства не расширяют scope. Новое атомарное утверждение не дедуплицирует и не закрывает целиком legacy-запись с несколькими независимыми фактами.
- Срок временного плана нельзя переносить на всю составную запись. Возраст упоминания, дата рождения и завершение события сами по себе не делают постоянный или исторический факт недействительным. Основной и фоновый planning-update используют общую защиту атомарности и subject/predicate; после успешной записи новой версии старая сохраняет исходный текст со статусом superseded, без принятия сгенерированного mergedContent за новое свидетельство.
- `retentionPolicy:durable` отделяет устойчивость знания от importance/anchor. Она выводится из существующего temporalScope и доказанного источника без отдельного AI-router; составные, производные и слабые выводы не повышаются. Qdrant блокирует автоматические TTL, замену и удаление защищённого утверждения, сохраняет историю явной owner-поправки и допускает явное удаление владельцем. Аудит читает архив явно через includeArchived; terminal-status не попадает в обычный recall. Подробности: docs/memory-retention.md.
- При реконсолидирующей поправке content/object/negated описывают одно утверждение. Существующая строгая проверка требует object как дословный фрагмент content в той же грамматической форме; словарная форма при склонении не проходит проверку. Не ослаблять эту границу fuzzy-сопоставлением для записи и связывания людей — корректный контракт передаётся в существующий semantic-вызов.
- Мутации одного факта сериализуются внутри account-worker; delayed caller передаёт expectedAssertion и при необходимости isActive. Ошибка чтения/отсутствие записи не разрешает upsert старого ID; очистка проверяет свежую версию. Счётчики доступа не меняют confidence; независимость подтверждения определяется стабильными sourceMessageIds, а не индексом скользящего окна. Отложенное извлечение передаёт predicate/object/negated/confidence и дословную цитату пользователя; повтор источника не является новым свидетельством. Owner-поправка сохраняет прежний provenance в lifecycleHistory, новое утверждение получает текущий источник; сильная привязка к человеку не переносится обычной текстовой поправкой.
- Продолжение `contacts.getProfile` связывает короткое подтверждение с кандидатом из структурированного результата своего ожидающего вызова. Ядро передаёт этот результат до удаления старого observation; текст истории его не заменяет. Один подтверждённый кандидат читается по ID/username с проверкой того же ID; несколько кандидатов, отрицание и пустой список не разрешают автоматический выбор. Этот контракт общий для Telegram и отдельной API-сессии и переживает сериализацию.
- Неопознанная естественная реплика при уточнении профиля возвращается в существующую intent-классификацию с сохранённым вопросом и кандидатами, а не исполняется как буквальное имя. `telegramProfileSelection` выбирает только ID из этого результата; смена темы проходит обычную маршрутизацию. Ожидающий runtime не допускается в fastDialogue. Склонения имён дают только кандидатов с уточнением, не доказательство личности.

- Админка MCP управляет общим реестром `servers`, Money Maker является только шаблоном. Валидация конфигурации и подключение к MCP общие для runtime и админки (`utils/mcpConfig.js`, `utils/mcpConnection.js`); оба JS-модуля должны попадать в сборку, SDK — разрешаться из общего родительского `node_modules` в admin image. Проверка читает ограниченный постраничный каталог без вызовов и автоматической выдачи прав. API маскирует headers/env/clientSecret значением `null`; сохранение `null` разрешено лишь для прежней цели подключения, OAuth-секрет дополнительно привязан к параметрам клиента. Изменение одного сервера не переписывает остальные конфигурации; общий revision защищает от устаревших и конкурентных сохранений.

- Автоматический выбор MCP использует существующую intent-классификацию и общий локальный каталог описаний/разрешённых имён с бюджетом, без отдельного AI-router и сетевого обхода всех серверов на каждую реплику. Название сервиса в просьбе не обязательно; общая тема не переводит объяснение или recall в MCP. Реальные схемы читаются только у выбранных сервисов, зависимые аргументы строятся после результата предыдущего вызова. ID источника результата задаёт исполненный вызов, не ответ провайдера; он сохраняется в контексте и observations при составных запросах.

- `details.mcpServers` — проверяемые ID из той же JSON-классификации, включая объединение составных частей. Список — подсказка источников, не выдача прав на запись. Для выбранных ID можно сразу получать схемы; пустой/недостаточный выбор допускает локальное discovery. Нельзя дублировать read/write-правила в fastDialogue поверх единого контракта классификации. Полный predicate рефлексии допускается только на уже выбранной OpenAI Luna, без замены модели даже при разрешённом fallback; ошибка Decisions возвращает прежний JSON-вызов. Этот predicate приоритизирует буфер, не отправляет уведомление. Исходящие, пересылки и старые сообщения не расходуют cooldown нового входящего triage.

- Исследование categorical routing сохраняется в `docs/decisions-research.md`. Короткий MCP-router не является заменой общего классификатора и его action details; дополнительный последовательный вызов нельзя считать ускорением по одной его задержке. Увеличение reasoning и простая переформулировка read/write-инструкции не исправили маршрутизацию на контрольной корзине. Независимые вопросы Decisions давали противоречивый доступ и выбор MCP; согласованный вывод доступа не устранил все ошибки памяти. Один predicate с полной инструкцией — кандидат для отдельного триажа, но сокращение критериев ухудшило контроль. Пороги подбираются только на calibration, не validation; снятие `allowFallback=false` не является способом включить другой endpoint вопреки закреплённому маршруту.

- MCP интегрируется в skills runtime через явные инструменты и отдельный `mcp.json` каждого аккаунта. Credentials оператора не наследуются tenant-ами, модель не задаёт endpoint/auth, а эффект инструмента определяется локальным allowlist, не `readOnlyHint`. Внешний вызов требует подтверждения точных аргументов и write-ahead квитанции; `unknown` не повторяется. Money Maker использует POST JSON-RPC без SSE/replay и `full` structuredContent. Рыночный анализ требует реальных свечей; поддержка загрузки по ticker/figi определяется актуальным каталогом сервера. При наличии серверной загрузки не переписывать свечные массивы через модель. JSON ошибки MCP остаётся в контексте обработки, summary для пользователя должно быть коротким и безопасным. Схемы каталога должны доходить до планировщика в пределах общего бюджета контекста; их нельзя удалять вместе с крупными обычными payloads. Некорректный граф или повторный ID отклоняется до выполнения и исправляется новым планом в пределах лимита шагов. Подробности: docs/mcp.md. Приоритет raw callResults и provenance выше дублирующего rolePayload: нельзя обрезать JSON общим префиксом и вытеснять первые результаты повторным каталогом при синтезе. Явный MCP не заменяется вебом/research/браузером после ошибки; дополнительный веб требует details.mcpAllowWeb из той же классификации новой просьбы. HTTP 429 и неверные параметры различаются без раскрытия provider payload; автоматический replay не добавляется.

- Контекст отправленного изображения — короткое русское описание готовой картинки (для детерминированной карты — её маркеров), с исходной пользовательской просьбой как fallback. Оно проходит вместе с `ProcessingResult` через merge/dedup и сохраняется только после отправки фото, с `kind:image` в истории и привязкой к message ID для reply; английский image prompt не попадает в историю. Фото и разговорный текст остаются отдельными сообщениями. Извлечение фактов и эпизодическая память исключают `kind:image`, а суммаризация сохраняет атрибуцию сюжету картинки. Подробности: docs/outgoing-image-context.md.
- `mergeRuntimeResults` переносит описание и исходную просьбу в каждый image artifact; общий и регулярный транспорт сохраняют контекст каждого успешно отправленного фото. Единственный artifact без flat-полей результата нельзя отбрасывать при объединении.

- Retrieval передаёт `MemoryRecallSummary` до конечного conversation synthesis (включая deferred и `memory.search`), отдельно от строковых сводок. Personal lookup отвечает по общему контракту свидетельств, без self-memory/биографии/эволюции и без подмешивания устаревшей dialogueSummary после фактов. Историческое свидетельство можно излагать исторически; неизвестная актуальность не отменяет найденное. Focus сохраняет domains и стратегию продолжения, новая тема не наследует их. `includeConversations` из семантического плана допускает отдельный ограниченный блок прямых scoped переписок в owner topic overview, никогда не пополняет owner fact pool и не доказывает трудоустройство/авторство проекта. Specific-контекст обязан сохранять subject, отрицание и время. Проверять только попадание IDs в контекст недостаточно: синтетический live eval проходит настоящее ядро и разговорный слой; production-аудиты по умолчанию остаются локальными read-only, без личных payloads провайдеру. Приватный прогон реальной корзины через модели допустим только после явного разрешения владельца с конкретным API и составом данных, без Telegram, memory writes и переноса реальных примеров в Git. См. docs/memory-answer-quality.md.

- Abstention `НЕОПРЕДЕЛЕНО` не является вторым намерением при проверке близости intent scores; реальные конкурирующие действия сохраняют уточнение. Semantic lookup не запускает операционный цикл из-за слов «задачи» или «напиши список»; explicit state skills, compound requests и subIntents сохраняют прежнюю обработку. Deictic reference не становится буквальным именем из-за ошибки `from=named`. Установленный typed identity path передаётся в ответ вместе с доказательством, без фильтра guessed domain или reranker. При точном identity-вопросе только scoped resolver может выставить identityVerified; конечный слой возвращает проверенное имя без повторной генерации и перестановки endpoint-ов. Broad «что помнишь о родственнике» не является identity-вопросом и сохраняет overview. В отношениях метка прямого источника переписки не меняет субъект факта и не доказывает общего работодателя. В overview конкретные записи предшествуют chapter/episode/user-schema, чтобы производные сводки не занимали бюджет до личных деталей; новизна на продолжении имеет приоритет над этим порядком. `noNewEvidenceInPool` относится только к ограниченному пулу; старые записи остаются доступны для явного пояснения, но не подаются как новые. Model judge дополняется проверкой route, subject, identity proof и новых evidence; честный отказ при потерянной известной записи не считается успехом.

- `highlight` выбирает надёжный факт из установленного person scope без буквального rerank по слову «интересный». `people_list` — отдельный scoped collection recall, не owner profile top-k и не адресная книга: directory profile+owner, typed owner edges с направлением и прямые sourceMessageIds частной переписки в выбранном домене. Переписка доказывает сохранённое обсуждение, не трудоустройство; subject/contact evidence не превращается в user fact. Один evidence bucket на человека/основание сохраняет разнообразие при пагинации. Коллекция сохраняет topic focus без произвольного обрезания до четырёх людей; новые инструменты действий из неё не авторизуются. Полнота ограничена каталогом/scan budget, группы и тёзки не сливаются.

- Лимит evidence pool применяется к допущенным записям, а не к первым raw points: subject/source/status фильтр передаётся в bounded pagination. Отдельный scan budget ограничивает чтение даже при полностью неподходящих страницах. Нельзя решать нехватку контекста ослаблением owner attribution. Частичная фамилия/компонент имени допустимы только в read-only recall после scoped alias/component matching и проверки уникальности; насыщенная страница из 12 кандидатов остаётся неоднозначной. Этот matcher не используется для записи/отправки/слияния. В owner topic overview разнообразие оценивается также по сохранённому predicate, а сомнение в актуальности одной детали не отменяет остальные известные факты.

- В skills runtime естественные вопросы памяти не проходят через `maybeStartContactMemoryLookup`: этот legacy-matcher принимал произвольную многословную тему за имя. Сохранённые уточнения/кнопки остаются совместимыми. Пустой `relationPath` при `from=owner` означает аутентифицированного автора текущей реплики, только при явной ссылке на себя из её текста; роль близкого человека требует сохранённого пути. В тематическом owner overview до трёх валидированных domains ограничивают bounded пагинацию, но не задают личность. Owner recall использует явный user-subject и общий фильтр атрибуции; нельзя ослаблять его до совпадения userId коллекции или переносить контактные/source-chat записи в профиль владельца. Ответ меняет перспективу пользовательского «мой» на «твой».

- `MemoryQueryPlan.requestKind=relationship` ищет историю взаимодействий запрошенных людей; `relationPath` устанавливает личность, а не утверждает или угадывает искомую связь. Не переходить от явно названного человека к его коллеге в вопросе «что нас связывает». Обзор отношений читает identity pool и оба endpoint tags, различает сохранённую пару и контекст; общая тема/источник переписки не доказывают сотрудничества. При двух названных людях owner↔person edges не заменяют связь между ними. В skills runtime не запускать legacy role-to-name resolver после canonical recall. Автоматические regression-наборы используют только синтетические payloads; replay личной памяти по умолчанию локальный, без providers и записей. Исключение для явно разрешённого приватного прогона описано выше.

- Общий memory recall использует семантический `MemoryQueryPlan` из существующего query-generation вызова: ссылки — кандидаты для чтения, не доказательства и не ID модели. Люди разрешаются только по scoped реестру/сильным ключам и сохранённым направленным relation paths; неоднозначность не снимается частотой или совпадением имён. `memoryRecallFocus` — отдельный owner/channel/TTL-bound поисковый контекст с evidence IDs, не разрешение доменных действий; хранится в сессии и копируется в deferred snapshot, recurring-run его очищает. Overview читает bounded paginated identity pool и выбирает разные виды фактов без embeddings/реранкера; specific использует grounded person scope и вопрос в hybrid/rerank. Не заменять этот механизм добавлением regex для отдельных ролей. Подробности: docs/entity-aware-memory-recall.md.

- Точный личный recall использует общий `fetchAgentMemoryContext` для foreground и dialogue jobs. Сохранённые owner↔person связи читаются до multi-query и защищены от потери в reranker; lookup реестра строго profile+owner+ID. Старые person IDs можно сопоставлять только по сильному Telegram ID, не по совпадению имени. Безымянная роль не создаёт `third_party` личность и не является кандидатом на имя. Действующие разные endpoints остаются неоднозначными. Короткие вопросы о близких и работе выполняются синхронно даже при ошибочном memoryNeed=none; «не найдено» не значит «пользователь не сообщал». Подробности: docs/personal-memory-recall.md.

Все credentials редактируются inline на одной странице с подразделами, выбор текстовых/локальных/голосовых/image моделей — только на странице моделей; внешность остаётся в «Личность». Отдельный image override подчиняется тому же правилу. Не вводить второй env-флаг с противоречащим состоянием и не называть прокси отдельным провайдером/моделью. Унаследованный URL показывается через allowlist с маскированием credentials; явный пустой env override имеет приоритет. URL проверяется до любых записей; ключи не передаются в URL. Анимировать можно только сохранённые directed `derived_from/episode` (источник → запись), не identity/semantic/отношения людей. Число частиц ограничено 24, частота — 30 fps, reduced-motion и скрытая вкладка отключают анимацию. Раскладка пути меняется только в клиенте, после выхода восстанавливается; фиксированные/hover координаты берутся после синхронной обработки Sigma. Полный текст читается отдельно с прежними profile/domain/user checks, без векторов и мутаций. Полный экран сохраняет фильтры, ограничивает фокус и возвращает scroll/focus после Esc.
- Выбор моделей объединён в автоматическую стратегию и Custom. Автоматическая принимает строго `{quality: standard|high|maximum, provider?: auto|openai|gemini|zai|openrouter}`; по умолчанию API выбирает система. Явный API фиксирует текстовые маршруты без fallback. Custom принимает одного корневого provider (openai/gemini/zai/openrouter/lmstudio) и все TEXT_TASKS с model только из каталога этого провайдера, maxTokens и reasoningEffort: никаких per-task provider, presetName, identity/credentials/ENV-ссылок от клиента. Сервисный профиль выводит сервер по провайдеру; `customProvider` в сохранённой политике подтверждает единообразие текстовых маршрутов. Старые смешанные Custom/ручные планы читаются без записи; редактор требует явного выбора одного провайдера перед новым сохранением. Сохраняются точные модели и параметры без localRole, чтобы позднее редактирование старых LM-ролей не меняло стратегию. UI отделяет сохранённое «Сейчас работает» от выбранного черновика. Автоматическая стратегия явно обозначена API; локальный тумблер существует только в редакторе Custom. Кнопка перехода к локальной настройке открывает черновик Custom, отмена возвращает прежний выбор, включение/отключение требует сохранения и не меняет runtime при чтении. Старые ручные профили показываются как Custom без записи в БД. Новые API/Custom-планы — version 3; quality-only остаётся version 2. Version-1 cost-метаданные нормализуются low→standard, medium→high, high→maximum, точные маршруты/параметры/allowFallback не меняются. Профиль памяти сохраняется; наличие credentials проверяется только в переданном окружении аккаунта. `AI_MODEL_POLICY` и `AI_MODEL_PRESET` записываются атомарно. Scoped preset приложения, фоновые снимки и запреты fallback сохраняют изоляцию. Уровень не является денежной квотой и не включает AI-фон. URL/ключи принимает только операторский config API.

- Точные проверки связи обрабатываются до классификации и retrieval без AI и фонового job; reply/forward, pending-state и составные просьбы не входят в этот путь. Для точных социальных реплик ошибочный memory/defer от модели не является основанием для исследования. Нельзя превращать приветствие или проверку связи в автоматический пересказ self-memory и событий дня.
- Основной orchestration runtime этой ветки — `orchestration/runtime`: классификация и единая подготовка памяти предшествуют адаптивному циклу инструментов; простой личный текст может завершиться совместным вызовом классификации и ответа до retrieval. `KIRA_ORCHESTRATION_MODE=legacy` сохраняет прежний planner/executor для отката. Скиллы в `skills/*/SKILL.md` являются процедурными инструкциями, не источником прав. Бизнес-сервисы прежних агентов переиспользуются через типизированные инструменты, без копирования identity/evidence/confirmation логики в prompts. Нельзя возвращать линейную маршрутизацию по единственному intent для составных запросов.
- Быстрый диалог использует маршрут `fastDialogue` общего preset registry и решение answer/review/defer/route в одном вызове. Личный/актуальный источник не допускает неподтверждённого предварительного ответа; действия и активные подтверждения остаются в каноническом потоке. Фоновый разбор — долговечная одноразовая задача `dialogue_jobs`, привязанная к profile/channel/turn, со снимком контекста и preset исходного хода. Только allowlist read-инструментов и research, без доменных мутаций, экспорта и self-evolution. Первый ответ предшествует активации; смена хода и отмена отсекают позднюю постановку и результат старого worker-а. Неопределённая доставка не повторяется. API получает продолжение через scoped polling; legacy/рубильник возвращают обычный путь. Подробности: `docs/fast-dialogue.md`.
- Асинхронное продолжение API включается только явным `Prefer: respond-async`; без него клиент получает полный синхронный ответ. Предпочтение входит в отпечаток идемпотентности, при этом прежние синхронные квитанции сохраняют свой формат. Gateway и account proxy передают заголовок и `Preference-Applied`, результат остаётся в канале приложения.
- Любая state/external-операция нового ядра требует успешно сохранённой write-ahead квитанции в сессии своего канала. `unknown` запрещает автоматический повтор; параметры и эффекты валидируются до вызова. Модель не задаёт account/user/session identity. Сохранение reminder выполняет инструмент, транспорт учитывает `remindersPersisted` и не сохраняет повторно. Финальный разговорный слой read-only и описывает действия только по квитанциям.
- Делегирование использует ограниченные агенты с одной целью и явным жизненным циклом; независимые исследования могут выполняться параллельно, родитель ожидает результат. Метаданные переживают рестарт, но не восстанавливают сами по себе живой browser/negotiation процесс. Уточнение или подтверждение не должно терять исходную составную цель; отмена завершает её очередь.
- Workflow-инструмент получает собственные типизированные параметры, а не детали чужого основного intent. Доменные ошибки и частичное сохранение должны передаваться статусами; строка с текстом ошибки не является успешным результатом. Подтверждение связывается с конкретной операцией, уточнение сохраняет исходный вызов и его зависимости. Ledger статусов зависимостей не сокращается вместе со свидетельствами для модели. Списки ресурсов ограничиваются страницами с фильтром, сохраняя ID и `nextOffset`.
- Возобновление сначала восстанавливает скиллы сохранённой очереди: lazy loading не должен вытеснять уже запланированный шаг. Доменные callback-и передают ядру подтверждённый результат по ключу операции; переход «период → личность» заменяет ключ того же ожидающего шага. Кнопки контактной памяти имеют стабильный ID уточнения, который не меняется при частичном сохранении. Чужое pending-состояние в сессии не определяет статус текущего инструмента. Конфликт фонового уточнения личности с живым диалогом приостанавливает задачу, сохраняя текущий вопрос и частичные артефакты.
- Регулярные задания используют отдельный `agentRuntimeStorageKey` (`task:<chatId>:<taskId>`) и идентификатор запуска по scheduled time. Ни write-ahead, ни доменный `persistSessionNow` не пишут их снимок поверх активной Telegram-сессии. Ожидающее продолжение переносится контролируемым merge; `unknown/needs_input` сразу приостанавливают расписание, а `failed` учитывается как ошибка. Канал доставки остаётся прежним.
- Ожидающий браузер не перехватывает самостоятельную новую команду. Продолжение и отмена используют ключ конкретной browser session, а не общее имя `agents.start`; отмена и неизвестный исход не завершают зависимость успехом. Live browser lookup/cancel проверяют серверный scope канала или task ledger. Общая owner-lane сериализует доступ к личному профилю браузера: второй канал получает явный отказ при ожидающем сценарии; незавершённую страницу нельзя молча заменить. Ручное продолжение фонового браузера сохраняет исходный ledger и ограничения recurring-run.
- `KIRA_DECISIONS_ENABLED` — опциональная замена категориального классификатора, не ещё один обязательный AI-вызов и не генератор свободных аргументов. Используется capability выбранного провайдера и существующий gateway; provider-pure Gemini/local не переходят скрыто на OpenAI. Без доступного Decisions обычная классификация сохраняется. Подробная карта и ограничения: `docs/agent-runtime.md`.
- Мультипользовательский API запускается отдельным сервисом `platform/`: bearer аккаунта выбирает только его runtime, а Telegram-владелец доказывается одноразовым приватным `/start`, без user/chat IDs из HTTP. Каждый аккаунт получает процесс, PostgreSQL DB/роль, стабильный UUID-based Qdrant namespace и runtime-каталог; process-global singleton-ы нельзя использовать для нескольких аккаунтов в одном процессе. Worker env строится по allowlist: личные credentials, personality и память оператора не наследуются; личная Telegram-сессия принимается лишь после проверки того же владельца. Токены ботов/сессии шифруются account-bound AES-GCM, API-токены хешируются; постоянный master key резервируется отдельно. Один manager удерживает PostgreSQL session-lock; потеря lease останавливает workers. Браузеры workers обязательно используют DNS-pinned прокси публичных сетей, включая loopback bypass и запрет прямого WebRTC/QUIC; без прокси браузер не запускается. Прежний владелец после локального импорта является обычным аккаунтом того же менеджера, без отдельной привилегированной роли в API.
- Перенос существующего инстанса выполняется только доверенным локальным `scripts/migrateCurrentAccount.py`: он проверяет running env и Compose identity, сохраняет исходные PostgreSQL/Qdrant namespaces и IDs, выдаёт обычному аккаунту отдельную ограниченную DB-роль и переносит только его runtime-файлы и personality. Подписанные API-действия, прежний ключ и порт сохраняются; служебная БД регистрации для этой DB-роли недоступна. `existingStorage` и API-key override принимаются только из локального импорта, никогда из HTTP. Исходная схема импортированного инстанса не синхронизируется от ограниченной роли: будущие schema migrations выполняются оператором. `KIRA_ACCOUNTS_MODE=true` переключает local.sh на менеджер аккаунтов; прежний bot service остаётся в профиле legacy для отката и не должен одновременно polling-ить тот же токен.
- Публичный gateway отделён от runtime: VPS проксирует только известные `/api/v1` routes через Tailscale Serve, проверяя upstream TLS/SNI. После перехода на сервис аккаунтов клиентский сертификат устройства не требуется: только POST регистрации и входа доступны без Bearer, остальные маршруты требуют токен аккаунта. Регистрация и вход имеют отдельный IP-лимит, AR-кадр — отдельный лимит тела 4 МиБ. Проверки API нельзя переносить на весь nginx server, если он также обслуживает публичный сайт. На VPS не копируются runtime env, токен владельца или ключ клиентского CA. Tagged VPS должен иметь grant только к API-порту хоста; широкие allow-all правила нельзя считать ограниченными добавлением узкого grant. Личные deployment-конфиги создаются только в ignored `runtime-data/`; сами шаблоны gateway не превращают API одного владельца в многопользовательский сервис.
- Стандартный референс вымышленной Киры — продуктовый ресурс `assets/characters/kira/reference.png`, который хранится в Git и копируется в bot/admin runtime. Личный `runtime-data/image-generation/character-reference.image` имеет приоритет; удаление личного override восстанавливает стандартный файл, не изменяя продуктовый asset. Нельзя исключать стандартный эталон из поставки вместе с приватными пользовательскими изображениями.
- Генерация изображений независима от текстового preset: `IMAGE_GENERATION_SETTINGS` в `bot_settings` задаёт модель GPT Image, размер, качество и выключатель; `OPENAI_IMAGE_API_KEY`/`OPENAI_IMAGE_BASE_URL` — необязательные env overrides поверх обычного OpenAI gateway. Существующий вызов подготовки image prompt одновременно возвращает `includesCharacter`, без второго классификатора. Сцена с персонажем требует канонический продуктовый референс либо личную замену из приватного `runtime-data/image-generation`; референс передаётся реальными bytes в `/images/edits`, обычная сцена идёт в `/images/generations`. Нельзя молча генерировать новое лицо при отсутствии референса или подменять облачный image-маршрут текстовой моделью. Base64 сохраняется в ограниченные по времени runtime-файлы и отправляется через `InputFile`, включая API-транспорт; содержимое референса, prompt и тело provider-ошибки не логируются.
- Внешний API — дополнительный канал того же runtime: использует существующие command/text/callback handlers с ожидаемой до конца обработкой текста и транспортом, преобразующим ответы в JSON. `ctx.chat.id`/`ctx.from.id` задаются сервером по владельцу и сохраняют общий scope знаний, напоминаний и задач. Диалог API хранится отдельно под `api:<ownerId>`; `sessionStorageKey` обязателен для его отложенных flush и анализа фактов, черновики отправки тоже разделяются по каналу. Нельзя принимать user/chat IDs или сырые callback data от клиента. Подтверждения подписываются, привязаны к последнему ходу API и сроку действия, а квитанции мутаций в PostgreSQL защищают от повторов после потери ответа; неизвестный результат после сбоя не разрешает автоматическое повторное выполнение. Плановые уведомления доставляются в Telegram; одноразовый разбор API-диалога возвращается через `/dialogue-jobs` и историю своего API-канала.
- Режим текста мобильного приложения — scoped override, а не второй глобальный preset. `bot_settings.API_AI_MODEL_PRESET` (JSON с ревизией, compare-and-set) применяется через `runWithChannelPreset` (AsyncLocalStorage) только на время API-хода. Его читают все `get*/refreshActiveAiPresetName`, включая политику fallback. Таймеры и автоматическая отложенная работа после окончания хода видят глобальный preset. Явное одноразовое продолжение ответа сохраняет preset исходного хода в долговечной задаче и открывает собственный scope worker-а. Каталог и доступность для приложения берутся из реестра и `admin-panel/presetAvailability.js`, без отдельного списка моделей. Нельзя переключать глобальный `AI_MODEL_PRESET` ради выбора в приложении или хранить выбор только на клиенте.
- AR-ходы мобильного приложения (`api/scene.ts`) — ходы того же API-диалога, что `/messages` и `/photos`, а не отдельный путь.
  - Слова проходят те же text handlers и оркестратор, что `/messages`, кадр — тот же `handleOwnerPhoto`, что `/photos` и фото из Telegram. Поэтому в комнате работают напоминания, память, поиск и картинки, а ответ — обычный `messages[]` с кнопками и файлами. Нельзя возвращать отдельный «AR-промпт» с одним вызовом модели: из-за него в комнате не работало ничего, кроме разговора.
  - Комната попадает в ход только как контекст `ctx.arRoom` (имена предметов и поза Киры, без ID и координат): в `enrichedContextFromMemory` текста, в контекст `processImage`/`processRuntimeImages` кадра. Быстрый диалог для AR-хода отключён, иначе ответ не увидит комнату.
  - Получатель кадра — модель чтения фото (`photoVisionRoute`, задача `conversation`) в режиме приложения; недоступная модель отклоняет ход до квитанции. Что Кира прочла с кадра, пишется в историю с `kind: 'image'` и не идёт в извлечение фактов; слова владельца идут как обычно. Кадры нигде не сохраняются.
  - Действия тела — только `sit/stand/approach/lookAtUser/point` над ID присланной сцены. Их выбирает отдельный короткий вызов `intentClassification` параллельно с ответом; его сбой оставляет ответ без действий. Исполнение и итог остаются за телефоном (`/scene/action-results`), итог пишется в тот же диалог словами телефона, без ID.
  - `sit` без `targetId` — выбор места телефоном по его LiDAR-скану (`autoSeat`). Сервер не выбирает сиденье и не принимает координаты от модели. Простое «садись» без действия дополняется детерминированно (`wantsPlainSit`), но не при «не садись» и не сидя.
  - `api-scene:<ownerId>` хранит только предложенные действия; прежняя отдельная история AR там очищается.
  - `point` — показать рукой, где лежит вещь. Классификатор даёт только `label` и, если есть, `targetId` запомненной вещи (`scene.things`, их хранит телефон) или предмета комнаты. При кадре вещь ищет на нём модель чтения фото режима приложения (задача `conversation`, тот же получатель кадра, что разрешил владелец) и возвращает только точку и рамку на картинке, 0–1000 → 0–1; в комнату её переносит телефон по своей глубине LiDAR. Сервер не принимает от модели координаты комнаты. Несколько таких вещей (`count > 1`), низкая уверенность, рамка почти на весь кадр, точка за кадром или сбой поиска — действия нет, в `rejectedActions` код (`ambiguous`/`unsure`/`not_found`), а запомненная вещь показывается по старому месту. При кадре выбор действий и поиск идут до ответа, и ответ получает итог поиска: слова совпадают с жестом или просят уточнить/навести камеру. Короткий ответ на такой вопрос («чёрный», «теперь видно?») телефон шлёт с новым кадром и `followUp {label, reason}` (минута после вопроса, не больше двух ответов); если классификатор не выбрал другое действие, та же вещь ищется на новом кадре, а слова ответа идут в поиск как уточнение (`detail`). Свободный текст уточнения на телефон не уходит. Заодно модель называет другие мелкие вещи на кадре (`seen`), телефон их запоминает. Вещи приходят только именами, возрастом и названием мебели, без координат.

Параметры генерации передаются адаптеру вместе с выбранной моделью; только LM Studio трактует локальный reasoning switch и лимит. - Каждый Docker Compose-стек идентифицируется через `KIRA_INSTANCE_NAME`:

  - безопасный default для серверного workflow выводится из имени каталога; перед Compose-командой запрещено продолжать, если тот же project name уже принадлежит другому working directory.

  - физические имена storage отделены от project identity через `POSTGRES_VOLUME_NAME` и `QDRANT_VOLUME_NAME`; по умолчанию они выводятся из `KIRA_INSTANCE_NAME`, но при переименовании project могут сохранять прежние значения.
  - перед Compose-командами mount существующих `postgres` и `qdrant` обязан совпадать с ожидаемыми `POSTGRES_VOLUME_NAME` и `QDRANT_VOLUME_NAME`; несовпадение блокирует deploy до запуска контейнеров.
  - server workflow не должен использовать `volume prune`, `docker volume rm`, `compose down -v` или `system prune --volumes`.
  - install/deploy не выполняет глобальные container/image/builder prune; операции очистки должны быть ограничены текущим Compose project.
  - direct и remote workflow используют общий `server-common.sh` preflight; дополнительные remote-инстансы живут в отдельных каталогах.
  - remote-deploy разрешает только legacy-каталог `/root/source` и прямой дочерний каталог `/opt/docker/<instance>`; пути к `/`, системным каталогам, вложенным директориям и сегментам `.` / `..` должны отклоняться до загрузки архива.
  - compose `.env` записывается атомарно только после успешных project/storage checks; неудачный preflight не должен менять существующий файл.
  - перенесённая вместе с каталогом compose `.env` является fallback-источником identity: простое переименование папки не должно создавать новый project/storage; явная смена имени выполняется через `migrate-instance`, который сохраняет прежние volumes aliases.
  - admin-порт работающего контейнера текущего инстанса допустим для redeploy; для остановленного собственного контейнера обязательно отдельно проверяется host listener.
  - legacy remote-deploy без `KIRA_INSTANCE_NAME` выводит имя Compose project из remote-каталога (`/root/source` → `source`), чтобы существующие `source_*` volumes не подменялись новыми пустыми volumes.
  - `.kira-admin-state` и compose `.env` содержат секреты, обязаны быть исключены из Git, иметь права `600` и храниться отдельно для каждого инстанса.
  - файловое runtime-состояние инстанса живёт только в его `runtime-data/`, смонтированном в `/app/runtime-data`; оно не входит в image/archive и не очищается remote-распаковкой. Общий preflight переносит legacy `/usr/src/app/dist/data` или `/usr/src/app/data` только когда целевая папка пуста.
- Фоновые Telegram-каналы имеют разные контракты:
  - DM Report — утилитарное дословное напоминание только о подтверждённых Telegram unread старше таймера; `(chatId,messageId)` является ключом, а чтение никогда не выполняется от имени владельца;

Новый фрагмент для дневной карточки содержит только входящие сообщения; исходящие реплики владельца допустимы лишь как контекст;
  - Inbox Guardian — максимум три grounded-наблюдения с реальными message ID, мнением Киры и одним действием; простой unread не является сигналом, AI error/неуверенность означают молчание без сырого fallback.

Локальная опора использует только явно известный город, любая опора принимается лишь при наличии прямого источника и сохраняется в provenance сообщения. Ошибка поиска не блокирует цикл, но запрещает выдумывать актуальные внешние детали.
  - Текущее место жизни персонажа является отдельным mutable-состоянием в `bot_settings` и не выводится из города происхождения, учёбы или старых глав биографии. Из диалога его может менять только владелец явной просьбой о переезде; админка редактирует то же состояние. Успешный разговорный переезд добавляет событие и главу self-memory, а локальный Kira Life всегда считает runtime-residence авторитетным.

- True-full AI preset-ы сохраняют провайдера при аварийной деградации:
  - после исчерпанного управляемого runtime retry тяжёлая Gemini-модель переходит по same-provider цепочке деградации (`gemini-3.5-flash-lite` → `gemini-3.1-flash-lite` → `gemini-2.5-flash-lite`), а не на одну lite-модель; цепочка упорядочена, и каждое дно исключает уже испробованные модели, чтобы не зацикливаться и доходить до самого дешёвого дна;
  - провайдер-специфичная политика (retry, same-provider degradation chain, парсинг идентичности ошибки вроде `x-goog-request-id`) обязана жить только в контракте провайдера (`AiProviderAdapter.getRetryPolicy` / `getSameProviderDegradationChain` / `parseErrorIdentities`), без дублирующего preset/JSON-реестра; admin availability проверяет пользовательские маршруты и credentials, а внутреннюю policy защищают contract-тесты; при добавлении нового провайдера (включая локальные модели) общий код не правится — policy реализуется в файле провайдера;
  - policy-методы вызываются с receiver адаптера, а общий runtime валидирует их результат: same-provider chain не принимает модель другого провайдера и сканируется до первого ещё не опробованного кандидата;
  - preset перечитывается между retry; при смене provider/model состояние предыдущего маршрута (`retries`, `triedModels`, последняя упавшая модель) сбрасывается целиком и не может продолжить старую degradation chain;
  - cross-provider fallback на GPT (`fallback-models.json`) остаётся runtime-политикой последнего рубежа и применяется только к пресетам, не являющимся true-full; true-full пресеты принципиально provider-pure и не падают на GPT;
  - retry primary включается провайдерной политикой только для true-full пресетов (без cross-provider подушки), и её `maxAttempts` авторитетен даже при значении `0`; для гибридов и GPT-пресетов остаётся базовый 1 retry + cross-provider fallback, чтобы не менять их поведение;
  - provider SDK не должен выполнять скрытые retry поверх runtime retry-flow;
  - Gemini SDK, прямые HTTP-вызовы и ожидание semaphore slot используют ограниченные timeout-ы, а file operations имеют отдельный увеличенный timeout;
  - Gemini Interactions вызывается через стабильный `/v1` с `store: false`, а usage читается из полей `usage.total_*`; для моделей 3.5/3.6 deprecated sampling-параметры (`temperature`, `top_p`, `top_k`) и OpenAI `n` (неподдерживаемый multi-candidate режим) должны удаляться провайдерным адаптером до HTTP-вызова;
  - file-backed transcription не использует model degradation chain: аудио до 12 MiB передаётся inline, крупное — через Files API; чтение/upload и inference ограничены единым deadline, удаление remote-файла получает короткое recovery-окно, допускается максимум один retry, а timeout не повторяется;
  - фактическое переключение модели обязательно логируется отдельным событием `[AI DEGRADED]` с безопасной диагностикой причины.
- Reminder-flows, которые продолжаются следующим сообщением пользователя после callback-кнопки, считаются context-critical и должны переживать отдельные Telegram updates через session storage.
- Действие «Помоги выполнить» у сработавшего личного напоминания является одноразовой передачей задачи в обычный orchestration pipeline: безопасные шаги выполняются доступными инструментами, внешние действия сохраняют свои подтверждения, а исходное напоминание не закрывается автоматически.
- Повтор напоминания обязан вычислять время строго позже текущего момента:
  - интервалы меньше часа считаются через миллисекунды без календарного округления;
  - после рестарта пропущенные интервальные срабатывания не воспроизводятся пачкой — создаётся только ближайшее будущее;
  - некорректный или не продвигающий время recurrence не планируется, а следующая запись сохраняется в БД до регистрации таймера.
- Регулярные фоновые задачи отделены от напоминаний:
  - напоминание повторно доставляет сохранённый текст, а recurring task заново выполняет исходный пользовательский запрос;
  - recurring task создаётся как любой поддерживаемой однофразовой командой с расписанием, так и следующим сообщением со ссылкой на предыдущий завершённый запрос; расписание отделяется от prompt, а prompt на каждом запуске проходит обычный orchestration pipeline;
  - due-задачи забираются через DB lock с восстановлением stale lock после рестарта, чтобы несколько runtime-процессов не дублировали запуск;
  - задача хранит ограниченный снимок контекста до исходного запроса и исполняется без текущих transient-state живого диалога;
  - длительная формулировка сохранённого запроса нормализуется в одноразовую команду на каждом запуске; внешний recurring scheduler уже задаёт время, поэтому неявный reminder intent/step внутри запуска запрещён, а явная команда создать напоминание остаётся допустимой;
  - фоновый recurring-run не входит в интерактивный `unclearIntent`/quick-choice flow: близкие intent scores разрешаются в пользу лучшего допустимого маршрута, а случайный `unclearIntent` step заменяется детерминированным fallback-планом;
  - ручной запуск и мутации используют атомарную проверку lock, а scheduler не ждёт завершения всей предыдущей пачки перед заполнением освободившихся worker-слотов;
  - интерактивное управление доступно через `/tasks`, разговорные команды паузы, возобновления и удаления и admin-panel, работающую с той же таблицей `recurring_tasks`; по текстовому описанию автоматически изменяется только единственное совпадение, при неоднозначности бот обязан запросить уточнение.
- Contact-aware memory logic должна быть централизована:
  - правила идентичности контакта, tag-based matching и проверки subject-а не дублируются по модулям;
  - retrieval, proactive hints и memory-gap должны использовать одни и те же helper-ы contact-memory.
  - `contact_username` считается сильным identity key наравне с `contact_id`, но не заменяет backward-compatible теги `contact_name/contact_alias/contact_key`.
- Conversational memory retrieval является гибридным:
  - candidate scope применяется до top-k; conversational dense отбирается по релевантности без раннего штрафа за возраст, а full-text использует отдельные bounded AND/OR пулы. Raw cosine и ranking старых storage/dedup callers не меняются;
  - owner-атрибутированный заголовок главы/модели не является contact prefix; смешанные/source-chat и contact записи не получают это исключение;
  - LLM-reranker принимает только номера показанных кандидатов или NONE; malformed/error означает ограниченный fallback. Кеш зависит от owner, всего вопроса, содержания кандидатов и лимита. Token packing сохраняет порядок реранкера и ограничивает также первый длинный факт. Background deepen отключает access/importance reinforcement через trackAccess:false. Карта и ограничения: docs/memory-retrieval-pipeline.md;
  - dense cosine, нормализованные lexical overlap и entity match объединяются только в multi-query recall; raw cosine из vector service остаётся неизменным для dedup, contradiction и storage-порогов;
  - entity match влияет только на порядок уже разрешённых contact scope кандидатов и не является механизмом идентификации или авторизации смешения людей;
  - Qdrant full-text payload index на `content` добавляется без изменения vector schema; его недоступность должна деградировать поиск до dense-only, а не блокировать запуск;
  - изменения формулы fusion закрепляются обезличенным eval-набором с recall@k, MRR и forbidden-hit метриками, а не подбираются только по единичному диалогу.
- Memory Atlas в админ-панели является read-only представлением существующей Qdrant-памяти:
  - browser API получает только компактный payload без embedding-векторов;
  - граф строится из сохранённых `relatedIds`, `sourceMemoryIds`, `sourceEpisodeId`, `person_id` и доказуемых person-relation tags, без квадратичного similarity-перебора при открытии страницы;
  - крупная раскладка выполняется ForceAtlas2 в Web Worker, а рендер — через Sigma.js/WebGL; graph bundle загружается лениво только при открытии атласа.
- Каждый пользовательский ход представляется как структурированный `ConversationTurn`:
  - `userText` содержит только новую реплику и является единственным входом для regex, intent/source routing и быстрого извлечения фактов;
  - reply/forward metadata передаются отдельно и не склеиваются с пользовательским текстом;
  - контекст отправленных rich/proactive сообщений должен переживать рестарт вместе с `messageId`, типом карточки, `contact_id/person_id` и memory IDs.
- Источник знаний выбирается до contact-memory и планировщика:
  - `personal` и `assistant_self` используют соответствующую память;
  - устойчивые общие сведения могут отвечаться без сети;
  - изменчивый внешний мир (`текущий`, новости, турниры, результаты, расписания, цены, правила, афиша) всегда идёт через `webSearch → conversation`;
  - при сомнении между стабильным и актуальным источником выбирается веб-поиск; личная память может только персонализировать запрос;
  - решение об источнике не заменяет основной action-intent: reminder/send/maps/browser сохраняются, а `webSearch` добавляется в их план только как источник актуального контекста;
  - произвольная именная группа после «что знаешь про» не считается человеком без person-сигналов.
- Каноническая память о людях строится из атомарных утверждений:
  - stable `person_id` является первичным внутренним ключом, имя и fuzzy-match используются только для поиска кандидатов;
  - единственный provisional-кандидат по точному alias переиспользует тот же UUID и может быть повышен до resolved при появлении сильного Telegram ID; исключение — личность, явно созданная через «Новый человек»: она остаётся отделённой от контактов до отдельного подтверждения;
  - reply metadata → Telegram ID/username → активная личность → подтверждённый alias → полное имя; одиночное неоднозначное имя не связывается автоматически;
  - одна запись содержит один `subject/predicate/object`; `content`, `object`, subject/contact tags, status, отрицание и temporal fields обязаны быть согласованы;
  - бинарная связь людей хранится в той же evidence-backed memory-записи, а не в отдельном источнике правды: оба конца разрешаются через stable `person_id` (владелец — специальный endpoint `user`), точное имя третьего лица обязано присутствовать в evidence, а vector dedup учитывает пару endpoint-ов и тип связи;
  - прямая поправка применяется к текущему ответу сразу, но долговременный patch разрешён только при доказанном субъекте и отсутствии добавленной причинности, хронологии или эмоций;
  - составную legacy-запись нельзя реконсолидировать заменой всей строки: сначала read-only audit/dry-run, затем подтверждённое split/supersede отдельных предикатов.
- Reflection не выводит субъект из источника чата. `subject:contact` допустим только при явном имени/обращении или местоимении с сохранённым speaker label; голое «я/ты» без автора не доказывает субъекта. Потерянный референт остаётся `unknown/third_party`, а antecedent-контекст входит в evidence-цепочку.
- В активном пользовательском ходе допускается один итоговый ответ и максимум один необходимый CTA/вопрос. Contextual proactive hints, memory-gap и implicit reminder не отправляются конкурентными fire-and-forget сообщениями; внутренний пайплайн `webSearch → conversation` не отправляет отдельные progress-сообщения; плановые фоновые сообщения остаются отдельным каналом. Быстрый диалог имеет явное исключение: начальный ответ, одно необходимое уведомление об углублении и существенное дополнение от привязанной долговечной задачи; устаревшие и дублирующие дополнения подавляются.
- Утверждения ассистента не являются доказательством фактов о пользователе:
  - Kira Life опирается только на self-memory и не может выводить из неё задачи, планы, обещания или дедлайны владельца; живые обращения, вопросы, шутки и новые предложения допустимы, а отдельный semantic-review блокирует лишь приписывание уже существующего неподтверждённого обязательства; безопасный fallback хранится с отдельным outcome, использует само событие текущего цикла и сохраняет только его фактический provenance, не наследуя детали отклонённой разговорной формулировки;
  - смешанные диалоговые эпизоды имеют `subject:system`, а вопрос, сомнение или отрицание пользователя не подтверждает предыдущую реплику бота;
  - `bot/system/contact/unknown` записи централизованно исключаются из любого user-синтеза, включая chapters, schemas и sleep-cycle; смешанный эпизод нельзя превращать в новую запись с `subject:user`;
  - `memoryInsight` использует только подтверждённые пользовательские записи, исключая episodes/chapters/schemas и bot/system/contact/unknown evidence.
- Форматирование Telegram-сообщений разделено на два слоя:
  - структурные/системные сообщения (дайджесты, списки, карточки, сводные отчёты, напоминания, меню) идут через единый DSL в `utils/richMessage.ts` (`sendStructured`/`editStructured`/`editStructuredCtx`), который рендерит rich-HTML для Bot API 10.1 (`sendRichMessage` / `editMessageText({rich_message})`) с автоматическим фолбэком на `sendMessage({parse_mode:"HTML"})`;
  - если Telegram отвергает и HTML из-за parse/entity-ошибки конкретного payload, структурный helper повторяет отправку без форматирования; `GrammyError` классифицируется по серверному `description`, а не по имени метода в общем `message`;
  - свободные ответы LLM в диалоге остаются plain text без parse_mode — бот намеренно сохраняет «человеческий» стиль, и форматирование туда не добавляется;
  - экранирование пользовательских данных (имена, тексты напоминаний, названия чатов, факты памяти) обязательно через `esc()`/`escAttr()` перед вставкой в блоки;
  - аварийный рубильник rich-форматирования — `RICH_MESSAGES_ENABLED` (по умолчанию `true`).
- Long polling обязан иметь глобальный `bot.catch`: непойманная ошибка одной команды логируется безопасно и не должна останавливать обработку следующих Telegram updates.
- Редактирование Telegram-сообщений должно быть идемпотентным:
  - текст и inline-клавиатура одного сообщения изменяются одним атомарным запросом;
  - полные text+markup и отдельные markup-only изменения проходят через одну per-message очередь; разные типы edit-запросов нельзя сериализовать независимо;
  - отдельные markup-only изменения проходят через общий helper с проверкой состояния;
  - `message is not modified` нельзя подавлять как штатную ошибку — no-op запрос не должен отправляться в Telegram.
- Personality defaults обязаны соответствовать `characterGender` и в runtime, и в admin-panel; при смене рода можно заменять только неизменённые системные defaults, но не пользовательские persona/biography.

## Что куда документировать
- `README.md`: пользовательские сценарии, настройка, эксплуатация и высокоуровневое описание возможностей. Не дублировать туда внутренние implementation details.
- `CHANGELOG.md`: хронологический список заметных изменений для владельца/пользователей проекта; писать человеческим языком, не превращать в git-log.
- `CODEX.MD`: долговечный инженерный контекст для будущих Codex-сессий: архитектурные решения, локальные соглашения и запреты на уже признанные ошибочными подходы. Не добавлять сюда каждую фичу, тест или путь к helper-файлу, если это не меняет устойчивое правило разработки.
- `ROADMAP.md`: планы и направления работ; не использовать как журнал уже сделанных изменений.

## Локальные соглашения
- Приватная идентификация запуска задаётся окружением (`KIRA_ALLOWED_USER_ID`, `KIRA_ADMIN_USER_ID`, `KIRA_BOT_USERNAME`, `OWNER_*`, `USER_*`) и ignored personality/runtime-файлами. Встроенного положительного user ID и даты рождения быть не должно; неизвестный или невалидный ID разрешает доступ никому. `npm run check:privacy` проверяет проект, `.githooks/pre-commit` — содержимое индекса Git; локальные env/personality используются только для поиска совпадений, найденные значения не выводятся. Проверка текущих файлов не очищает ранее опубликованную Git-историю.
- Реальные персональные данные владельца и его окружения запрещено переносить из production-памяти, диалогов, логов и диагностических отчётов в исходный код, тестовые fixtures, snapshots, комментарии и документацию. Regression-примеры должны использовать явно синтетические имена, ID и события; пользовательский `personality.json` считается отдельной локальной конфигурацией, а не источником fixtures.
- Commit message пишутся в формате Conventional Commits: `<type>(optional-scope): <summary>`.
- Рекомендуемые типы: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`, `revert`.
- `summary` и тело коммита пишутся по-русски.
- Тело коммита опционально. Его стоит добавлять только когда без него теряется контекст решения, мотивация или важное ограничение.
- Если тело коммита есть, оно должно быть коротким и практичным; обычно достаточно блока `Зачем`, иногда вместе с кратким `Что сделано` или пометкой о `BREAKING CHANGE`.
- Подробные шаги проверки, длинные списки изменений и развёрнутые риски должны жить в Pull Request, а не в каждом commit message.
- Пример: `fix(ops): добавить вывод логов без postgres`.
- TypeScript smoke/regression tests в `scripts/test*.ts` запускаются через общие раннеры:
  - `npm run test:ts -- <file>` для одиночного теста;
  - `npm run test:ts:ai`, `test:ts:memory`, `test:ts:interaction`, `test:ts:all` для групповых прогонов.
- Production stage в `admin-panel/Dockerfile` должен автоматически забирать корневые runtime-модули админки через `COPY admin-panel/*.js ./`, а не через ручной список файлов:
  - если в корне `admin-panel/` появляется новый server-side `.js`-модуль, он должен попадать в runtime-образ без отдельной правки Dockerfile;
  - для не-JS runtime-артефактов (`.json`, `src/*`, общие файлы из `ai/` и `utils/`) всё ещё нужно явно проверять копирование в production stage.
