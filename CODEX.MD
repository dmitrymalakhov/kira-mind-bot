# CODEX

## Назначение файла
- `AGENTS.md` в корне — кросс-платформенная точка входа для coding agents; он должен отправлять агент к `CODEX-RULES.MD` и `CODEX.MD`.
- `CODEX-RULES.MD` в корне хранит обязательные правила репозитория и имеет более высокий приоритет, чем остальные локальные markdown-файлы.
- `CODEX.MD` в корне проекта хранит локальный инженерный контекст именно для `kira-mind-bot`.
- Глобальный `../CODEX.MD` не редактируется для проектных деталей, которые относятся только к этому репозиторию.

## Архитектурные решения
- Каждый Docker Compose-стек идентифицируется через `KIRA_INSTANCE_NAME`:
  - project name, постоянные volumes и имя bot-контейнера должны быть уникальны для инстанса;
  - внутренние service DNS (`postgres`, `qdrant`, `kira-mind-bot`) остаются одинаковыми внутри изолированных сетей;
  - admin-panel получает физическое имя bot-контейнера через `KIRA_BOT_CONTAINER_NAME`, поэтому мониторинг и restart не должны возвращаться к глобальному хардкоду `kira-mind-bot`;
  - session-cookie админки должна иметь уникальное имя на основе `KIRA_INSTANCE_NAME`, потому что браузер не изолирует cookie одного host по разным портам;
  - host-порты общих инфраструктурных сервисов не публикуются без явной необходимости, а `ADMIN_PORT` обязан различаться между инстансами.
  - при миграции старой установки существующие `ADMIN_*` сначала читаются из compose `.env`, а затем сохраняются в локальном `.kira-admin-state`; state-файл конкретного инстанса имеет приоритет.
  - безопасный default для серверного workflow выводится из имени каталога; перед Compose-командой запрещено продолжать, если тот же project name уже принадлежит другому working directory.
  - при первом запуске admin-порт выбирается из свободных `7000–8999`; занятый порт старого собственного контейнера допустим при redeploy, порт чужого project — нет.
  - физические имена storage отделены от project identity через `POSTGRES_VOLUME_NAME` и `QDRANT_VOLUME_NAME`; по умолчанию они выводятся из `KIRA_INSTANCE_NAME`, но при переименовании project могут сохранять прежние значения.
  - перед Compose-командами mount существующих `postgres` и `qdrant` обязан совпадать с ожидаемыми `POSTGRES_VOLUME_NAME` и `QDRANT_VOLUME_NAME`; несовпадение блокирует deploy до запуска контейнеров.
  - server workflow не должен использовать `volume prune`, `docker volume rm`, `compose down -v` или `system prune --volumes`.
  - install/deploy не выполняет глобальные container/image/builder prune; операции очистки должны быть ограничены текущим Compose project.
  - direct и remote workflow используют общий `server-common.sh` preflight; дополнительные remote-инстансы живут в отдельных каталогах.
  - remote-deploy разрешает только legacy-каталог `/root/source` и прямой дочерний каталог `/opt/docker/<instance>`; пути к `/`, системным каталогам, вложенным директориям и сегментам `.` / `..` должны отклоняться до загрузки архива.
  - compose `.env` записывается атомарно только после успешных project/storage checks; неудачный preflight не должен менять существующий файл.
  - перенесённая вместе с каталогом compose `.env` является fallback-источником identity: простое переименование папки не должно создавать новый project/storage; явная смена имени выполняется через `migrate-instance`, который сохраняет прежние volumes aliases.
  - admin-порт работающего контейнера текущего инстанса допустим для redeploy; для остановленного собственного контейнера обязательно отдельно проверяется host listener.
  - legacy remote-deploy без `KIRA_INSTANCE_NAME` выводит имя Compose project из remote-каталога (`/root/source` → `source`), чтобы существующие `source_*` volumes не подменялись новыми пустыми volumes.
  - `.kira-admin-state` и compose `.env` содержат секреты, обязаны быть исключены из Git, иметь права `600` и храниться отдельно для каждого инстанса.
  - файловое runtime-состояние инстанса живёт только в его `runtime-data/`, смонтированном в `/app/runtime-data`; оно не входит в image/archive и не очищается remote-распаковкой. Общий preflight переносит legacy `/usr/src/app/dist/data` или `/usr/src/app/data` только когда целевая папка пуста.
- Фоновые Telegram-каналы имеют разные контракты:
  - DM Report — утилитарное дословное напоминание только о подтверждённых Telegram unread старше таймера; `(chatId,messageId)` является ключом, а чтение никогда не выполняется от имени владельца;
  - reflection extraction сохраняет память без технических карточек; отдельный дневной фильтр под управлением `DAYTIME_REFLECTION_ENABLED` запускается только после критичного `highPriority`-сигнала, отправляет максимум две grounded-карточки в календарные сутки с persistent-дедупликацией источников, а бытовые и обычные незакрытые сообщения оставляет вечернему Guardian;
  - Inbox Guardian — максимум три grounded-наблюдения с реальными message ID, мнением Киры и одним действием; простой unread не является сигналом, AI error/неуверенность означают молчание без сырого fallback.
  - Kira Life выполняет веб-поиск только перед внешним проактивным событием, а не во время частых внутренних циклов; тип реальной внешней опоры не ограничен каталогом и выводится из текущей жизненной линии, биографии и интересов self-memory. Локальная опора использует только явно известный город, любая опора принимается лишь при наличии прямого источника и сохраняется в provenance сообщения. Ошибка поиска не блокирует цикл, но запрещает выдумывать актуальные внешние детали.
- Live health/monitoring для внешних систем должен жить отдельным диагностическим слоем:
  - bot runtime публикует узкие internal health endpoints;
  - admin backend агрегирует их вместе с infra/API checks;
  - бизнес-логика бота не должна содержать admin-oriented monitoring orchestration.
- Мониторинг Telegram user-client (`services/telegram.ts`) должен читать только рабочие поля GramJS `telegram@^2.26.22`:
  - `client.connected` (геттер → `sender.isConnected()` → `_userConnected`) для transport-состояния;
  - `sender.isReconnecting` (без подчёркивания) для состояния reconnect;
  - приватные поля `sender._disconnected` (всегда `true`), `client._reconnecting` и `sender._reconnecting` (всегда `false`) — мёртвые, их читать нельзя;
  - комбинировать `client.connected && !client.disconnected` некорректно — `client.disconnected` опирается на мёртвый `_disconnected` и всегда `true`, поэтому результат всегда `false`;
  - изменения transport-состояния логируются через подписку на `UpdateConnectionState` (`import { Raw } from "telegram/events"`, `import { UpdateConnectionState } from "telegram/network"`); значения: `connected=1`, `disconnected=-1`, `broken=0`.
- AI usage analytics считает токены только по `usage`, который вернул провайдер:
  - исходящий HTTP-трафик не используется как источник правды для токенов;
  - runtime пишет только дешёвые event-log записи в `ai_usage_logs`;
  - все агрегации, breakdown и time-series считаются только в admin backend по запросу UI.
- True-full AI preset-ы сохраняют провайдера при аварийной деградации:
  - после исчерпанного управляемого runtime retry тяжёлая Gemini-модель переходит по same-provider цепочке деградации (`gemini-3.5-flash-lite` → `gemini-3.1-flash-lite` → `gemini-2.5-flash-lite`), а не на одну lite-модель; цепочка упорядочена, и каждое дно исключает уже испробованные модели, чтобы не зацикливаться и доходить до самого дешёвого дна;
  - провайдер-специфичная политика (retry, same-provider degradation chain, парсинг идентичности ошибки вроде `x-goog-request-id`) обязана жить только в контракте провайдера (`AiProviderAdapter.getRetryPolicy` / `getSameProviderDegradationChain` / `parseErrorIdentities`), без дублирующего preset/JSON-реестра; admin availability проверяет пользовательские маршруты и credentials, а внутреннюю policy защищают contract-тесты; при добавлении нового провайдера (включая локальные модели) общий код не правится — policy реализуется в файле провайдера;
  - policy-методы вызываются с receiver адаптера, а общий runtime валидирует их результат: same-provider chain не принимает модель другого провайдера и сканируется до первого ещё не опробованного кандидата;
  - preset перечитывается между retry; при смене provider/model состояние предыдущего маршрута (`retries`, `triedModels`, последняя упавшая модель) сбрасывается целиком и не может продолжить старую degradation chain;
  - cross-provider fallback на GPT (`fallback-models.json`) остаётся runtime-политикой последнего рубежа и применяется только к пресетам, не являющимся true-full; true-full пресеты принципиально provider-pure и не падают на GPT;
  - retry primary включается провайдерной политикой только для true-full пресетов (без cross-provider подушки), и её `maxAttempts` авторитетен даже при значении `0`; для гибридов и GPT-пресетов остаётся базовый 1 retry + cross-provider fallback, чтобы не менять их поведение;
  - provider SDK не должен выполнять скрытые retry поверх runtime retry-flow;
  - Gemini SDK, прямые HTTP-вызовы и ожидание semaphore slot используют ограниченные timeout-ы, а file operations имеют отдельный увеличенный timeout;
  - Gemini Interactions вызывается через стабильный `/v1` с `store: false`, а usage читается из полей `usage.total_*`; для моделей 3.5/3.6 deprecated sampling-параметры (`temperature`, `top_p`, `top_k`) и OpenAI `n` (неподдерживаемый multi-candidate режим) должны удаляться провайдерным адаптером до HTTP-вызова;
  - file-backed transcription не использует model degradation chain: аудио до 12 MiB передаётся inline, крупное — через Files API; чтение/upload и inference ограничены единым deadline, удаление remote-файла получает короткое recovery-окно, допускается максимум один retry, а timeout не повторяется;
  - фактическое переключение модели обязательно логируется отдельным событием `[AI DEGRADED]` с безопасной диагностикой причины.
- Reminder-flows, которые продолжаются следующим сообщением пользователя после callback-кнопки, считаются context-critical и должны переживать отдельные Telegram updates через session storage.
- Действие «Помоги выполнить» у сработавшего личного напоминания является одноразовой передачей задачи в обычный orchestration pipeline: безопасные шаги выполняются доступными инструментами, внешние действия сохраняют свои подтверждения, а исходное напоминание не закрывается автоматически.
- Повтор напоминания обязан вычислять время строго позже текущего момента:
  - интервалы меньше часа считаются через миллисекунды без календарного округления;
  - после рестарта пропущенные интервальные срабатывания не воспроизводятся пачкой — создаётся только ближайшее будущее;
  - некорректный или не продвигающий время recurrence не планируется, а следующая запись сохраняется в БД до регистрации таймера.
- Регулярные фоновые задачи отделены от напоминаний:
  - напоминание повторно доставляет сохранённый текст, а recurring task заново выполняет исходный пользовательский запрос;
  - recurring task создаётся как любой поддерживаемой однофразовой командой с расписанием, так и следующим сообщением со ссылкой на предыдущий завершённый запрос; расписание отделяется от prompt, а prompt на каждом запуске проходит обычный orchestration pipeline;
  - due-задачи забираются через DB lock с восстановлением stale lock после рестарта, чтобы несколько runtime-процессов не дублировали запуск;
  - задача хранит ограниченный снимок контекста до исходного запроса и исполняется без текущих transient-state живого диалога;
  - длительная формулировка сохранённого запроса нормализуется в одноразовую команду на каждом запуске; внешний recurring scheduler уже задаёт время, поэтому неявный reminder intent/step внутри запуска запрещён, а явная команда создать напоминание остаётся допустимой;
  - фоновый recurring-run не входит в интерактивный `unclearIntent`/quick-choice flow: близкие intent scores разрешаются в пользу лучшего допустимого маршрута, а случайный `unclearIntent` step заменяется детерминированным fallback-планом;
  - ручной запуск и мутации используют атомарную проверку lock, а scheduler не ждёт завершения всей предыдущей пачки перед заполнением освободившихся worker-слотов;
  - интерактивное управление доступно через `/tasks`, разговорные команды паузы, возобновления и удаления и admin-panel, работающую с той же таблицей `recurring_tasks`; по текстовому описанию автоматически изменяется только единственное совпадение, при неоднозначности бот обязан запросить уточнение.
- Contact-aware memory logic должна быть централизована:
  - правила идентичности контакта, tag-based matching и проверки subject-а не дублируются по модулям;
  - retrieval, proactive hints и memory-gap должны использовать одни и те же helper-ы contact-memory.
  - `contact_username` считается сильным identity key наравне с `contact_id`, но не заменяет backward-compatible теги `contact_name/contact_alias/contact_key`.
- Memory Atlas в админ-панели является read-only представлением существующей Qdrant-памяти:
  - browser API получает только компактный payload без embedding-векторов;
  - граф строится из сохранённых `relatedIds`, `sourceMemoryIds`, `sourceEpisodeId`, `person_id` и доказуемых person-relation tags, без квадратичного similarity-перебора при открытии страницы;
  - крупная раскладка выполняется ForceAtlas2 в Web Worker, а рендер — через Sigma.js/WebGL; graph bundle загружается лениво только при открытии атласа.
- Каждый пользовательский ход представляется как структурированный `ConversationTurn`:
  - `userText` содержит только новую реплику и является единственным входом для regex, intent/source routing и быстрого извлечения фактов;
  - reply/forward metadata передаются отдельно и не склеиваются с пользовательским текстом;
  - контекст отправленных rich/proactive сообщений должен переживать рестарт вместе с `messageId`, типом карточки, `contact_id/person_id` и memory IDs.
- Источник знаний выбирается до contact-memory и планировщика:
  - `personal` и `assistant_self` используют соответствующую память;
  - устойчивые общие сведения могут отвечаться без сети;
  - изменчивый внешний мир (`текущий`, новости, турниры, результаты, расписания, цены, правила, афиша) всегда идёт через `webSearch → conversation`;
  - при сомнении между стабильным и актуальным источником выбирается веб-поиск; личная память может только персонализировать запрос;
  - решение об источнике не заменяет основной action-intent: reminder/send/maps/browser сохраняются, а `webSearch` добавляется в их план только как источник актуального контекста;
  - произвольная именная группа после «что знаешь про» не считается человеком без person-сигналов.
- Каноническая память о людях строится из атомарных утверждений:
  - stable `person_id` является первичным внутренним ключом, имя и fuzzy-match используются только для поиска кандидатов;
  - единственный provisional-кандидат по точному alias переиспользует тот же UUID и может быть повышен до resolved при появлении сильного Telegram ID; исключение — личность, явно созданная через «Новый человек»: она остаётся отделённой от контактов до отдельного подтверждения;
  - reply metadata → Telegram ID/username → активная личность → подтверждённый alias → полное имя; одиночное неоднозначное имя не связывается автоматически;
  - одна запись содержит один `subject/predicate/object`; `content`, `object`, subject/contact tags, status, отрицание и temporal fields обязаны быть согласованы;
  - бинарная связь людей хранится в той же evidence-backed memory-записи, а не в отдельном источнике правды: оба конца разрешаются через stable `person_id` (владелец — специальный endpoint `user`), точное имя третьего лица обязано присутствовать в evidence, а vector dedup учитывает пару endpoint-ов и тип связи;
  - прямая поправка применяется к текущему ответу сразу, но долговременный patch разрешён только при доказанном субъекте и отсутствии добавленной причинности, хронологии или эмоций;
  - составную legacy-запись нельзя реконсолидировать заменой всей строки: сначала read-only audit/dry-run, затем подтверждённое split/supersede отдельных предикатов.
- Reflection не выводит субъект из источника чата. `subject:contact` допустим только при явном имени/обращении или местоимении с сохранённым speaker label; голое «я/ты» без автора не доказывает субъекта. Потерянный референт остаётся `unknown/third_party`, а antecedent-контекст входит в evidence-цепочку.
- В активном пользовательском ходе допускается один итоговый ответ и максимум один необходимый CTA/вопрос. Contextual proactive hints, memory-gap и implicit reminder не отправляются конкурентными fire-and-forget сообщениями; внутренний пайплайн `webSearch → conversation` не отправляет отдельные progress-сообщения; плановые фоновые сообщения остаются отдельным каналом.
- Утверждения ассистента не являются доказательством фактов о пользователе:
  - Kira Life опирается только на self-memory и не может выводить из неё задачи, планы, обещания или дедлайны владельца; живые обращения, вопросы, шутки и новые предложения допустимы, а отдельный semantic-review блокирует лишь приписывание уже существующего неподтверждённого обязательства; безопасный fallback хранится с отдельным outcome, использует само событие текущего цикла и сохраняет только его фактический provenance, не наследуя детали отклонённой разговорной формулировки;
  - смешанные диалоговые эпизоды имеют `subject:system`, а вопрос, сомнение или отрицание пользователя не подтверждает предыдущую реплику бота;
  - `bot/system/contact/unknown` записи централизованно исключаются из любого user-синтеза, включая chapters, schemas и sleep-cycle; смешанный эпизод нельзя превращать в новую запись с `subject:user`;
  - `memoryInsight` использует только подтверждённые пользовательские записи, исключая episodes/chapters/schemas и bot/system/contact/unknown evidence.
- Форматирование Telegram-сообщений разделено на два слоя:
  - структурные/системные сообщения (дайджесты, списки, карточки, сводные отчёты, напоминания, меню) идут через единый DSL в `utils/richMessage.ts` (`sendStructured`/`editStructured`/`editStructuredCtx`), который рендерит rich-HTML для Bot API 10.1 (`sendRichMessage` / `editMessageText({rich_message})`) с автоматическим фолбэком на `sendMessage({parse_mode:"HTML"})`;
  - свободные ответы LLM в диалоге остаются plain text без parse_mode — бот намеренно сохраняет «человеческий» стиль, и форматирование туда не добавляется;
  - экранирование пользовательских данных (имена, тексты напоминаний, названия чатов, факты памяти) обязательно через `esc()`/`escAttr()` перед вставкой в блоки;
  - аварийный рубильник rich-форматирования — `RICH_MESSAGES_ENABLED` (по умолчанию `true`).
- Редактирование Telegram-сообщений должно быть идемпотентным:
  - текст и inline-клавиатура одного сообщения изменяются одним атомарным запросом;
  - полные text+markup и отдельные markup-only изменения проходят через одну per-message очередь; разные типы edit-запросов нельзя сериализовать независимо;
  - отдельные markup-only изменения проходят через общий helper с проверкой состояния;
  - `message is not modified` нельзя подавлять как штатную ошибку — no-op запрос не должен отправляться в Telegram.
- Personality defaults обязаны соответствовать `characterGender` и в runtime, и в admin-panel; при смене рода можно заменять только неизменённые системные defaults, но не пользовательские persona/biography.

## Что куда документировать
- `README.md`: пользовательские сценарии, настройка, эксплуатация и высокоуровневое описание возможностей. Не дублировать туда внутренние implementation details.
- `CHANGELOG.md`: хронологический список заметных изменений для владельца/пользователей проекта; писать человеческим языком, не превращать в git-log.
- `CODEX.MD`: долговечный инженерный контекст для будущих Codex-сессий: архитектурные решения, локальные соглашения и запреты на уже признанные ошибочными подходы. Не добавлять сюда каждую фичу, тест или путь к helper-файлу, если это не меняет устойчивое правило разработки.
- `ROADMAP.md`: планы и направления работ; не использовать как журнал уже сделанных изменений.

## Локальные соглашения
- Реальные персональные данные владельца и его окружения запрещено переносить из production-памяти, диалогов, логов и диагностических отчётов в исходный код, тестовые fixtures, snapshots, комментарии и документацию. Regression-примеры должны использовать явно синтетические имена, ID и события; пользовательский `personality.json` считается отдельной локальной конфигурацией, а не источником fixtures.
- Commit message пишутся в формате Conventional Commits: `<type>(optional-scope): <summary>`.
- Рекомендуемые типы: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`, `revert`.
- `summary` и тело коммита пишутся по-русски.
- Тело коммита опционально. Его стоит добавлять только когда без него теряется контекст решения, мотивация или важное ограничение.
- Если тело коммита есть, оно должно быть коротким и практичным; обычно достаточно блока `Зачем`, иногда вместе с кратким `Что сделано` или пометкой о `BREAKING CHANGE`.
- Подробные шаги проверки, длинные списки изменений и развёрнутые риски должны жить в Pull Request, а не в каждом commit message.
- Пример: `fix(ops): добавить вывод логов без postgres`.
- TypeScript smoke/regression tests в `scripts/test*.ts` запускаются через общие раннеры:
  - `npm run test:ts -- <file>` для одиночного теста;
  - `npm run test:ts:ai`, `test:ts:memory`, `test:ts:interaction`, `test:ts:all` для групповых прогонов.
- Production stage в `admin-panel/Dockerfile` должен автоматически забирать корневые runtime-модули админки через `COPY admin-panel/*.js ./`, а не через ручной список файлов:
  - если в корне `admin-panel/` появляется новый server-side `.js`-модуль, он должен попадать в runtime-образ без отдельной правки Dockerfile;
  - для не-JS runtime-артефактов (`.json`, `src/*`, общие файлы из `ai/` и `utils/`) всё ещё нужно явно проверять копирование в production stage.
